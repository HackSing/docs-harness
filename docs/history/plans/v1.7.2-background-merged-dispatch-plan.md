# v1.7.2 后台治理合并快路径方案：声明制合并 dispatch 与批量 progress

## 背景与目标

后台治理复杂路线（`background_goal`）的标准序列要求宿主执行 `prepare → dispatched → running → progress×N → verify` 共 5+N 次 CLI 往返（contracts.md 第 10 节）。对 `change_scoped` 估算且分数 < 60 的中小型复杂 Job，这些往返是固定税：每次往返的校验闸门（工件校验、绑定、attempt、工作包全集、指纹、路由合同复验）完全相同，只是被拆成多条命令。

**目标**：在不跳过任何既有校验闸门的前提下，提供两个声明制合并入口：

1. `background dispatch --job-status running --prepare-and-run`：单命令内顺序执行 prepare → contract_ready→dispatched 校验 → dispatched→running 校验，省 2 次往返；
2. `background progress --all completed`：一次把冻结 Plan 全部工作包从合法前置态推进到 completed，省 N-1 次往返。

## 设计要点

### A. `--prepare-and-run`（仅 dispatch）

- 声明制：必须显式同时给出 `--prepare-and-run` 与 `--job-status running`，缺一失败关闭（`invalid_background_job_status`）；不自动推断目标状态。
- 执行序列复用既有闸门实现，逐步等价于分步执行：
  1. `prepare_background_goal_artifacts`（repair=False）：已 prepared 且指纹一致时返回 `already_prepared` 语义跳过重写（幂等）；工件部分/无效/冲突时抛出与分步 prepare 完全相同的错误码；
  2. contract_ready→dispatched 校验与状态写入（goal_contract 存在、`validate_background_goal_artifacts` 全量复验、`dispatched_at` 与事件）；
  3. dispatched→running 校验与状态写入（工件复验、`knowledge_job_scope_changes` 漂移检测、锁获取、`started_at` 与事件）。
- 任一闸门失败即停在该步：prepare 闸门失败抛出与分步 prepare 相同的 HarnessError；dispatch 闸门失败返回与分步 dispatch 相同的结构化 payload（含相同 `next_action`/`next_command_argv`/`reason_code`），并附加 `prepare_and_run: true` 与 `completed_steps` 标明已完成的步数，不做任何后续步骤。
- 资格限制（合并前一次性判定，不合格不执行任何步骤）：
  - 仅 `execution_route == "background_goal"`；`background_goal_phased` 拒绝（分阶段合并边界不变），`background_direct` 拒绝（本来就直达，行为不变）；
  - 仅 `workload_estimate_ref` 指向的估算为 `estimate_basis == "change_scoped"` 且 `raw_score < 60`；
  - 拒绝时返回 exit 3 与受控原因码 `background_prepare_and_run_not_eligible`，并携带精确 `eligibility_reason_code`（`route_phased_oversized`/`route_not_complex_goal`/`workload_estimate_unavailable`/`estimate_not_change_scoped`/`score_not_below_60`），记录 `transition_rejected` 事件。
- 实现方式：把既有 dispatch 执行体抽取为 `dispatch_background_job_status(...)` 助手，分步路径与合并路径调用同一份代码，从结构上保证闸门语义不发散。

### B. `--all completed`（仅 progress）

- 声明制：`--all` 只接受 `completed` 一个值（parser choices 强制）；与 `--work-package-id`/`--work-package-status` 混用失败关闭。
- 推进语义：先整体预检——任一工作包处于非法前置态（`blocked` 或未知状态值）即整体拒绝，不写任何进度、返回阻断清单（`background_progress_all_blocked`，含每项 `id` 与 `status`，`partial_commit: false`）并记录一次 `progress_rejected` 事件；
- 预检通过后逐包推进：`pending → in_progress → completed`、`in_progress → completed`、已 `completed` 跳过（幂等），每一步都调用既有 `update_background_goal_progress` 状态机，事件逐包记录，与分步执行逐条一致。
- 预检保证推进阶段不会出现非法转换，因此不存在部分提交路径。

### C. 不变量

- 控制面不变量不动：后台 Job 仍不能直写 `job.json`/`plan.json`/`progress.json`/`events.jsonl`；合并路径写入仍只由 CLI 完成。
- `knowledge dispatch` 兼容别名共享同一路径与同一门禁（别名 parser 不带新参数，行为不变）。
- 文档路由合同复验（`governance_route_contract_drift`）在合并入口前照旧执行，不跳过。

## 验收标准

先写失败测试（命名 `test_v172_*`）：

- T1：`--prepare-and-run` 单命令从 contract_ready 到 running，事件序列（`created/prepared/dispatched/running`）与分步执行逐条一致；先分步 prepare 再 `--prepare-and-run` 时复用 `already_prepared` 语义不重复写事件；
- T2：闸门失败停在对应步骤——工件指纹漂移时与分步 prepare 返回相同错误码；知识基线漂移时停在 running 闸门，返回与分步 dispatch running 相同的 payload/next_action；
- T3：`--all completed` 批量推进成功且事件与逐包分步一致；含 blocked 工作包时整体拒绝、不部分提交、返回阻断清单；
- T4：phased 路线（`background_goal_phased`）与 `change_scoped` 分数 ≥60 的 Job 拒绝 `--prepare-and-run`，返回受控原因码；
- T5：分步路径行为不回归（既有后台测试全绿）。

全量 `python -m unittest tests.test_harness` 除已知无关失败（`test_cross_platform_task_detection`、`test_authorization_template_command`）外全绿；self-test、`release sync` 检查模式、`npm run pack:check` 通过。版本升 1.7.2，用自身 `release sync --apply --target-version 1.7.2` 自举完成四源同步。

## 安全边界

- 只做声明制合并，不自动推断：目标状态、资格都由显式参数与已冻结的估算记录决定。
- 所有既有校验闸门原样保留：工件校验、绑定、attempt、工作包全集、指纹、路由合同复验一个不少；失败出口与分步执行一致。
- `background_direct` 行为不变；phased 路线分阶段合并边界不变。
- `--all completed` 不部分提交：非法前置态整体拒绝。
- 不自动提交、推送 git；不触碰 fast_track 与 release sync 代码。
