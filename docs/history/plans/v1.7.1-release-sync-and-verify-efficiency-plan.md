# v1.7.1 发版同步与验收提效方案：单命令原子同步 + 验收层复用

## 背景与目标

效率审查识别出交付阶段的两笔固定税：

| # | 现象 | 根因 |
|---|------|------|
| 1 | 每次发版需手工核对 4 处版本一致（`VERSION`、`package.json`、SKILL.md frontmatter、`scripts/harness.py` 的 `VERSION` 常量 :26）+ CHANGELOG/contracts/托管指引同步，漏一处验收返工 | 无单命令原子同步入口；一致性靠人肉核对 |
| 2 | 源码、本地安装副本、Git HEAD/远端、fresh clone 四层验收各自独立执行，中间产物（快照指纹、SHA-256）重复计算 | 验收层独立判定是正确的，但层间中间产物无复用机制 |

**目标**：发版同步从多次手工核对收敛为单命令原子操作；多层验收在不改变独立性语义的前提下消除重复计算。

## 设计要点

### A. 单命令版本同步（`release sync`）

- 新增 CLI 命令 `release sync [--apply]`：
  - 默认（无 `--apply`）为检查模式：扫描四处版本真源 + CHANGELOG 顶部条目 + SKILL.md frontmatter，输出差异报告（JSON），exit code 区分"一致 / 不一致 / 缺失"。
  - `--apply --target-version X.Y.Z`：以 `scripts/harness.py` 的 `VERSION` 常量为唯一输入源，原子写入 `VERSION` 文件、`package.json`、SKILL.md frontmatter；任一文件写入失败即整体回滚（先全部写入临时内容校验，再统一替换）。
  - CHANGELOG/contracts 文案不做自动生成（语义内容），但检查模式报告"CHANGELOG 顶部条目版本号与目标不一致"作为提示。
- 只修改 Docs Harness 明确拥有的文件（遵循 preserve-and-merge 的受管文件原则），不触碰业务文档。

### B. 验收层中间产物复用

- **安全前提**：四层验收的判定结论保持独立，不互相替代（architecture.md 既有合同不变）；只复用层间的**确定性中间产物**：
  - 工作区快照指纹、安装副本 SHA-256 在单次 verify 会话内按（路径, 内容哈希）缓存，跨层传递；
  - 缓存键包含合同版本与目标 identity，合同/分支变化即缓存失效。
- fresh clone 与远端验证涉及网络 I/O，不做跳过优化，只保证不重复 clone 同一 commit。
- 复用命中/未命中写入 verify 响应的 `layer_reuse` 字段（有界遥测，不含路径以外信息），供账本观测提效效果。

## 验收标准

- 先失败测试：
  - T1：四处版本一致时 `release sync` 检查模式 exit 0，报告 `consistent`；
  - T2：人为制造 `package.json` 版本不一致 → 检查模式非零 exit，报告精确差异字段；
  - T3：`release sync --apply --target-version` 原子写入四处真源；模拟中途失败（只读目标文件）→ 无任何部分写入；
  - T4：同一次 verify 会话中跨验收层复用快照指纹，`layer_reuse` 字段记录命中；合同版本变化后缓存失效重算；
  - T5：四层验收判定结论仍各自独立产出（对照既有 delivery_layers 测试不回归）。
- `pytest tests/test_harness.py` 全量通过；evals 增加 release sync 用例。
- 版本升至 1.7.1（本方案交付时用自身的 `release sync --apply` 完成同步，形成自举验收）；CHANGELOG、contracts.md、todo.md 同步。

## 实施步骤

1. 本方案登记 + todo.md 相对链接。
2. 阶段 A：先写 T1–T5 失败测试。
3. 阶段 B：实现 `release sync` 检查与原子写入（含回滚）；登记 contracts.md 命令合同。
4. 阶段 C：实现验收层中间产物缓存（缓存键设计与失效规则），接入 verify 响应 `layer_reuse` 字段。
5. 阶段 D：更新 SKILL.md 与 `managed_agent_block` 指引；全量测试 + evals。
6. 阶段 E：用 `release sync --apply` 自举完成 1.7.1 版本同步，作为端到端验收。

## 安全边界

- 不改变验收层独立性语义：源码、安装副本、Git HEAD/远端、fresh clone 仍各自独立判定；只复用确定性中间产物，不复用判定结论。
- `release sync --apply` 只写受管文件；归属不明内容失败关闭（与 preserve-and-merge 一致）。
- 不自动提交、推送 git；版本同步结果由用户决定提交时机。

## 开放问题

- `release sync` 是否需要 dry-run diff 输出（建议：是，检查模式已含差异报告，可先不做完整 diff）。
- 中间产物缓存是否需要跨 CLI 进程的磁盘级持久化（建议：先只做进程内/会话内，磁盘级等有账本数据再评估）。

## 与方案一的顺序

- 方案一（v1.7.0 轻量准入通道）先行，直接对应"harness 耗时 ≤ 1/4"目标；本方案可独立并行或后置，二者文件改动区域基本不重叠（本方案新增 release 命令与 verify 缓存，不触碰准入路径语义）。
