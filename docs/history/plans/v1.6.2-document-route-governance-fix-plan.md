# Docs Harness v1.6.2 文档真源路由失败关闭修复方案

## 1. 方案状态

- 目标版本：`v1.6.2`
- 当前状态：Codex 与 Kimi CLI 已完成两轮只读联合审查，待授权实施
- 修复范围：仅 Docs Harness 源包中的控制器、配置合同、测试和源包文档
- 唯一方案真源：本文档
- 当前缺陷版本：文件快照自报 `v1.6.1`
- 当前验收层：只完成源码审计与方案审查；尚未修改实现、运行测试、提交、推送或发布

## 2. 背景与问题

`create_post_completion_governance_job()` 当前把治理文档路径直接写死在 Job 合同中：

- 估算写入范围固定为 `docs/adr/**`、`docs/reviews/**`、`docs/todo.md`、`CHANGELOG.md`；
- Job 读范围固定追加 `docs/**`、`CHANGELOG.md`；
- Job 写范围再次固定为上述四类路径。

项目配置 `docs-harness/project-config/v4` 的 `background_governance` 只有启用状态、工作量阈值和宿主派发策略，没有正式文档路由。结果是控制器无法区分项目真实使用的 Changelog、TODO、ADR、Review 或 Architecture 真源，也无法在路径有歧义时失败关闭。

这不是单个 Changelog 分支错误，而是治理文档缺少统一路由合同。若只替换一处 `CHANGELOG.md`，其他硬编码路径仍会重复制造同类问题。

## 3. 目标

本次修复必须实现以下产品结果：

1. 项目可以显式声明五类正式文档路径：`architecture`、`changelog`、`todo`、`adr_root`、`reviews_root`。
2. 显式配置始终优先；配置存在但非法时失败关闭，不能静默退回自动探测。
3. 未配置某一类别时，只接受受控候选集合中的唯一可信候选。
4. 多候选、无候选或不安全候选形成独立、可审计、零写权限的治理阻塞，不影响已经完成的父任务事实。
5. 后台 Job 不得创建 canonical 文件或 canonical 根目录；它只能在已经确认的真源文件上更新，或在已经确认的根目录内创建受控子文档。
6. 旧项目只有根 `CHANGELOG.md` 且它是唯一可信候选时，继续路由到该文件。
7. 已创建但缺少新路由合同的非终态治理 Job 只能读取状态，不能继续 prepare、dispatch、progress 或 verify；必须显式迁移到新 attempt。
8. 路由变化不能破坏 Job 去重、范围锁、基线检查或回滚边界。

## 4. 非目标

- 不修改父任务先完成、后台治理独立运行的双通道语义。
- 不修改知识初始化、知识增量或知识地图路由。
- 不修改文档 deliverable 分类规则；只把既有分类结果映射到正式路由类别。
- 不支持同一类别同时存在多个 canonical 文档。
- 不自动创建缺失的 Changelog、Architecture、TODO、ADR 根目录或 Review 根目录。
- 不修改任何业务项目、安装副本或业务文档。
- 不在本方案阶段提交、推送、发布或派发任何后台 Job。

## 5. 配置合同

### 5.1 配置形态

继续使用 `docs-harness/project-config/v4`，在 `background_governance` 下增加可选字段：

```json
{
  "background_governance": {
    "enabled": true,
    "non_blocking": true,
    "workload_estimator": "v1",
    "simple_threshold": 24,
    "complex_threshold": 59,
    "host_dispatch": "required_when_supported",
    "document_routes": {
      "architecture": "docs/architecture.md",
      "changelog": "docs/changelog.md",
      "todo": "docs/todo.md",
      "adr_root": "docs/adr",
      "reviews_root": "docs/reviews"
    }
  }
}
```

五个键均可选。缺少 `document_routes` 或缺少其中某个键，只表示该类别进入自动探测，不表示采用默认写入路径。

### 5.2 字段校验

每个显式路由值必须同时满足：

- 是单个非空字符串，长度不超过 512 个字符；
- 使用 POSIX 项目内相对路径；
- 不包含 glob、反斜杠、冒号、控制字符、绝对路径或 `..`；
- 不指向 `.git/**`、`.docs-harness/**` 或 Harness Runtime；
- `architecture`、`changelog`、`todo` 指向已经存在的常规文件；
- `adr_root`、`reviews_root` 指向已经存在的目录；
- 路径本身及从项目根到目标的每个已有父级都不是符号链接；
- `resolve()` 后仍位于项目根目录内；
- 返回和持久化磁盘上的实际大小写路径，保证指纹稳定。

配置中出现未知键、错误类型或非法路径时返回 `invalid_document_route_config`。配置存在但非法时不得退回自动探测。

## 6. 自动候选与可信判定

### 6.1 受控候选集合

自动探测只扫描项目根目录和 `docs/` 的直接条目，不递归：

| 类别 | 自动候选 |
|---|---|
| `changelog` | 根目录或 `docs/` 下 basename 大小写不敏感匹配 `changelog.md` 的文件 |
| `architecture` | 根目录或 `docs/` 下 basename 大小写不敏感匹配 `architecture.md` 的文件 |
| `todo` | 根目录或 `docs/` 下 basename 大小写不敏感匹配 `todo.md` 的文件 |
| `adr_root` | 仅 `docs/adr` 目录，名称大小写不敏感匹配 |
| `reviews_root` | 仅 `docs/reviews` 目录，名称大小写不敏感匹配 |

根级 `adr/`、`reviews/` 不自动认定为 canonical；有此类项目约定时必须使用显式配置。

### 6.2 大小写与唯一性

- 候选匹配使用 `casefold()`，但唯一性不能只按字符串 casefold 去重。
- 在大小写敏感文件系统上，两个仅大小写不同但实际为不同文件的候选必须判定为多候选。
- 只有指向同一实际文件身份的重复表示才可以合并；候选结果保存目录枚举得到的实际大小写路径。

### 6.3 解析结果

新增单一入口 `resolve_document_routes(target, *, required_kinds)`：

1. 只解析当前治理 deliverable 真正需要的类别。
2. 显式配置合法且目标可信时直接采用。
3. 未配置时，可信候选恰好一个才采用。
4. 多个可信候选返回 `document_route_ambiguous`。
5. 没有可信候选返回 `document_route_missing`。
6. 不安全候选不得作为可信候选，也不得因其他候选存在而被静默忽略；结果中记录有界的拒绝原因。

当前 `adr_changelog_todo_review` deliverable 映射到 `changelog`、`todo`、`adr_root`、`reviews_root`。`architecture` 先进入通用合同和测试，但没有明确 architecture deliverable 时不得扩大现有 Job 写入范围。

## 7. 路由合同与指纹

每个 `delivery_governance` Job 增加结构化路由合同：

```json
{
  "document_route_contract": {
    "schema_version": "docs-harness/document-routes/v1",
    "status": "resolved",
    "required_kinds": ["adr_root", "changelog", "reviews_root", "todo"],
    "routes": {
      "changelog": {"path": "docs/changelog.md", "source": "explicit", "type": "file"},
      "todo": {"path": "docs/todo.md", "source": "auto", "type": "file"},
      "adr_root": {"path": "docs/adr", "source": "auto", "type": "directory"},
      "reviews_root": {"path": "docs/reviews", "source": "auto", "type": "directory"}
    }
  },
  "route_base_key": "sha256:...",
  "route_contract_fingerprint": "sha256:..."
}
```

### 7.1 `route_base_key`

用于同一父任务治理 Job 的稳定去重，不包含可变化的路径：

```text
sha256(canonical_json({
  task_kind,
  parent_task_id,
  parent_package_fingerprint,
  sorted_deliverables
}))
```

同一 `route_base_key` 存在非终态 Job 时必须幂等返回原 Job，不能因配置修复或路由变化创建第二个治理 Job。

现有 `idempotency_key` 字段继续保留。对 `delivery_governance`，其值固定等于 `route_base_key`；其他 Job 类型维持当前算法。这样既保留 background-job/v2 的公共字段，又让治理 Job 的去重绑定最终父任务包和 deliverable，而不绑定可变化的路由结果。

### 7.2 `route_contract_fingerprint`

仅在解析成功时生成，绑定：

```text
schema_version + required_kinds + sorted(routes.kind/path/source/type)
```

该指纹不替代 `route_base_key`。估算的 `source_fingerprint` 和 `change_scope_fingerprint` 继续包含实际写入范围，保持现有估算语义。

## 8. Job 创建与阻塞流程

### 8.1 解析成功

`create_post_completion_governance_job()` 只调用一次路由解析器，并用同一结果派生：

- workload estimate 的 `allowed_write_scope`；
- Job 的 `allowed_read_scope`；
- Job 的 `allowed_write_scope`；
- `document_route_contract` 与指纹；
- 文档类别锁和路径锁。

写入范围生成规则：

- 文件类路由使用精确文件路径；
- `adr_root`、`reviews_root` 使用已解析根目录加 `/**`；
- 全部路径排序、去重后再计算估算和 Job 指纹；
- 不再保留任何独立硬编码 `CHANGELOG.md`、`docs/todo.md`、`docs/adr/**`、`docs/reviews/**` 分支。

### 8.2 解析失败

多候选或无候选仍创建一个独立治理阻塞 Job，但必须满足：

- 状态为 `needs_user_input`；
- `allowed_write_scope=[]`；
- 不把任何未确认候选加入读写授权；
- `route_contract_fingerprint` 为空；
- `document_route_contract.status=unresolved`；
- 只保存有界的类别、错误码和相对候选路径，不保存自由文本或绝对路径；
- 父任务完成事实保持不变；post-completion 返回 `action_required` 和阻塞 Job ID，不得伪装为普通 `dispatch_failed`。

需要为 `create_background_job()` 增加受控的初始阻塞合同入口。它只能由 `delivery_governance + unresolved route + empty write scope` 使用，其他 Job 不得任意指定初始状态。

### 8.3 非法显式配置的逐入口行为

非法显式配置不能静默回退，也不能落入通用 `dispatch_failed` 兜底。各入口行为固定如下：

| 入口 | 行为 |
|---|---|
| `run` 准入 | 不解析文档路由，不因路由缺失阻塞普通父任务；配置整体有效性仍按现有准入合同处理 |
| `verify` post-completion | 创建单一零写权限 `needs_user_input` Job；`document_route_contract.status=invalid_config`，reason code 为 `invalid_document_route_config`；父任务 verify 保持完成和 exit 0，post-completion 返回 `action_required` |
| `background retry` | 重新校验；仍非法则保持零写权限阻塞并返回 exit 3，不进入 `contract_ready` |
| `project check` | red：`invalid_document_route_config` |
| `project upgrade` preview | 列入 `manual_migrations`，`apply_completion_possible=false` |
| `project upgrade --apply` | 拒绝覆盖或静默保留非法值，返回 exit 3，要求先修正配置 |
| 通用 `background estimate` | 不新增隐式路由语义；只有内部创建 `delivery_governance` estimate 前必须先获得 resolved contract |

预期的 missing、ambiguous、invalid-config 都由解析器返回结构化结果；只有读取失败、JSON 损坏或内部不变量破坏才抛给通用异常兜底。

## 9. 重试、旧 Job 与升级迁移

### 9.1 新阻塞 Job 重试

`background retry` 对 unresolved 路由 Job：

1. 重新读取当前项目配置和文件候选；
2. 解析仍失败时保持 `needs_user_input`，不增加写权限，不重复创建 Job；
3. 解析成功时归档旧 attempt 工件、刷新基线、重建 scopes、写入路由合同与指纹；
4. 进入 `contract_ready`；复杂路线仍需重新 `prepare`；
5. 不把旧 scope 与新 scope 做并集。

### 9.2 旧治理 Job 判定

非终态 `delivery_governance` Job 缺少 `route_contract_fingerprint` 时视为 `legacy_governance_route_contract`：

- `background list|status` 保持只读可见；
- `prepare|progress|verify` 以及 `dispatch` 的所有非 `cancelled` 目标状态统一失败关闭；`dispatch --job-status cancelled` 是唯一允许的执行面迁移，用于进入安全修复前置状态；
- `updated|no_change|completed_with_finding|failed` 保持历史只读，不改状态、不改 scope；
- 所有需要恢复的旧 Job 必须先停止宿主执行，再通过现有状态报告入口显式进入 `cancelled`：

  ```bash
  python3 scripts/harness.py background dispatch \
    --target . \
    --job-id <job-id> \
    --job-status cancelled \
    --json
  ```

- `contract_ready|queued_manual|needs_user_input|needs_rebase|dispatched|running` 到 `cancelled` 使用现有状态图允许的取消迁移；控制器只记录宿主已经停止的状态，不声称能够主动终止外部宿主；
- 对缺少路由合同的 `cancelled` 治理 Job，扩展 `background retry` 为一次性 route repair：归档旧 attempt、重新解析、零并集重建 scope、写入新路由合同后进入 `contract_ready`；普通 cancelled Job 仍不可 retry；
- route repair 是控制器合同迁移，不消耗用户原有重试预算：`attempt` 和 `max_attempts` 同时增加 1，并记录 `legacy_route_contract_repaired` 事件，保证剩余执行重试次数不变；
- retry 前若 Job 不是 `cancelled`，返回 `legacy_governance_job_not_quiesced`，不得依赖无法验证的“宿主应该已停止”自由文本；
- 终态成功/发现/失败 Job 不允许 route repair；取消后的旧 Job 才能显式恢复。

### 9.3 `project upgrade`

升级预览必须列出：

- 配置是否存在非法 `document_routes`；
- 非终态旧治理 Job ID、状态和所需动作；
- `apply_completion_possible` 是否成立。

升级应用：

- preserve-and-merge 既有合法 `document_routes`；
- 缺少该字段时不自动回填探测结果，保留“每次创建 Job 时现场解析”的兼容语义；
- 不静默改写任何旧治理 Job 的状态或 scope；
- 即使存在旧 Job，脚本、配置和规则升级仍可完成，但整体状态必须返回 `needs_manual_migration`、exit 3，并列出所有待取消和 route repair 的 Job；不得返回 `upgraded`；
- `running|dispatched` Job 必须明确标记 `host_quiescence_required=true`；控制器不声称升级动作已经停止外部宿主；
- 不创建、修改或删除任何 canonical 文档。

## 10. 锁与并发

`background_lock_names()` 对治理 Job 返回两类锁的并集：

1. 现有路径锁：由最终 `allowed_write_scope` 派生；
2. 稳定类别锁：`document-kind-changelog`、`document-kind-todo`、`document-kind-architecture`、`document-kind-adr`、`document-kind-reviews`。

类别锁跨路径切换保持稳定，防止旧路径与新路径因锁名不同而并发双写。阻塞 Job 不持有写锁；进入 `contract_ready` 后按已解析合同重新获取。

## 11. 运行时复验与符号链接时间窗

创建 Job 时的路径安全检查不能覆盖创建后到实际写入前的符号链接替换时间窗。因此：

- `prepare`、`dispatch` 和 `verify` 前重新解析并核对 `route_contract_fingerprint`；
- 配置或路由目标变化时返回 `document_route_drift`，进入 `needs_rebase` 或 `needs_user_input`，不得继续运行；
- 基线指纹继续作为内容并发漂移兜底；
- 不宣称一次 `is_symlink()` 检查能够永久证明路径安全。

## 12. `project check` 与错误分级

| 场景 | 结果 |
|---|---|
| 显式配置字段非法、越界或不安全 | red：`invalid_document_route_config` |
| 当前存在 unresolved 治理 Job | yellow/action-required：返回 Job ID 和 reason code |
| 自动探测多候选但当前没有治理 Job | yellow：`document_route_ambiguous` |
| 自动探测无候选但当前没有治理 Job | yellow：`document_route_missing` |
| 旧非终态治理 Job 缺路由合同 | yellow/action-required；执行入口仍独立失败关闭 |
| 路由合同或目标漂移 | red 或 Job 级 `needs_rebase`，不得派发 |

文档路由缺失不能阻塞普通父任务准入；只有非法显式配置属于控制合同错误，需要在相关控制入口失败关闭。

## 15. 回滚边界

新增字段保持 project-config/v4 的可选扩展，因为仅升到 v5 不能让旧控制器的 `run` 路径失败关闭。真正的回滚边界是：

1. 控制器脚本和 `.docs-harness/config.json` 必须作为同一版本单元恢复；
2. 回滚前必须先执行 `project rollback-check`；恢复后、继续任务前必须执行 `project check`；
3. 存在非终态新路由合同 Job、unresolved Job 或旧 Job 迁移中间态时阻断回滚；
4. 只回滚控制器会让新创建的治理 Job恢复硬编码行为，因此属于禁止的混合版本状态；
5. 回滚不删除 Runtime、不改写历史 Job，也不删除项目文档。

## 16. 联合审查结论

Kimi CLI 首轮审查确认了三处硬编码、配置零校验、现有范围安全函数、Job 去重与锁之间的依赖，并提出通用路由解析器、unresolved 阻塞 Job、双层指纹和测试矩阵。

联合复核否决了两个初始建议：

1. 旧治理 Job 不能按旧硬编码范围继续运行，因为这可能主动创建第二套 canonical 文档；最终改为只读可见、执行面失败关闭、显式 retry 迁移。
2. 单纯升级配置 schema 不能保护回滚，因为旧控制器的 `run` 不会因 schema 不匹配而停止；最终采用 project-config/v4 可选字段，并把同版本控制器/配置恢复、rollback-check 和 project check 写成硬边界。

第二轮审查进一步确认：类别锁必须与路径锁并存；阻塞与已解析 Job 使用稳定 `route_base_key` 去重；自动候选只扫描根目录和 `docs/` 的受控名称；根级 ADR/Review 必须显式配置。

Codex 在最终收敛时补充了大小写敏感文件系统边界：只能合并同一实际文件身份，不能仅按 casefold 把两个不同文件误当作一个候选。
