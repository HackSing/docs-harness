# Docs Harness v1.6.1 后台 Goal 宿主桥接缺陷实现方案

## 1. 方案状态

- 目标版本：`v1.6.1`
- 当前状态：源码与临时项目实施完成，真实宿主、下游安装和 Git 交付待独立验收
- 实施状态：阶段 A-D 已完成；116 项源码回归、自检与打包检查通过
- 唯一真源：本文档
- 影响产品：仅 Docs Harness
- 不包含：下游项目升级、提交、推送、发布和真实宿主验收

当前已验证层级：

- 源码：`scripts/harness.py`、CLI、公共合同、版本真源与回归测试已同步到 `1.6.1`。
- 临时项目：非 Git 与 Git Runtime 均完成 prepare → dispatched → running → progress → verify 全链路；覆盖篡改、repair、retry、别名和在途兼容。
- 来源包：`npm test` 116/116、`npm run self-test`、`npm run pack:check` 均通过。
- 未验证：真实宿主 Goal/Plan 桥接、ZBuddy 或等价下游大仓、安装副本、Git HEAD/远端、fresh clone 与发布。

## 2. 背景

复杂后台 Job 使用 `background_goal` 或 `background_goal_phased` 路线时，控制器要求 Job Runtime 中存在绑定当前 `job_id` 与 `idempotency_key` 的 `plan.json` 和 `progress.json`。实际宿主可以建立应用内 Goal 和 Plan，但这些状态不会自动成为 Harness Runtime 工件。

当前合同存在以下断点：

1. Harness 校验 Goal 工件，却没有负责物化工件的正式 CLI。
2. `host_dispatch_contract` 直接给出 `retry → dispatched → running`，缺少进入 `dispatched` 前的准备动作。
3. 业务 Job 禁止写 `.git/**`，而 Git 项目的控制面 Runtime 位于 `<git-dir>/docs-harness/**`；当前文档没有明确区分业务数据面与 Harness 控制面。
4. Goal 工件缺失、无效或绑定错误时，只返回当次调用错误，Job 事件无法事后解释拒绝原因。
5. 废弃兼容入口 `knowledge dispatch` 保留了复杂路线校验旁路，可以跳过 `dispatched` 和 Goal 工件校验进入 `running`。
6. 增量 Job 的工作量评估仍以整仓规模为主，小范围变化可能仅因仓库较大被提升为 `background_goal_phased`。

`v1.6.0` 已实现 `changed_paths=[] → no_write_no_sync`，本方案不重复修改该行为。

## 3. 当前事实

### 3.1 已确认的缺陷

| 编号 | 缺陷 | 当前行为 | 产品影响 | 优先级 |
|---|---|---|---|---|
| BG-01 | Goal 工件没有生产入口 | 测试辅助函数直接写文件，正式 CLI 无对应动作 | 支持 Goal 的宿主仍无法按合同启动复杂 Job | P1，版本阻断 |
| BG-02 | 派发顺序缺少 prepare | Job 可先进入 `dispatched`，到 `running` 才发现工件缺失 | 形成“已派发但不可运行”的中间态 | P1，版本阻断 |
| BG-03 | 控制面写入所有权不清 | 业务范围禁止 `.git/**`，Harness 又要求 Runtime 工件位于其中 | 智能体可能拒绝合法控制面动作，或通过直接写文件绕过控制器 | P1，版本阻断 |
| BG-04 | 兼容别名绕过安全不变量 | `knowledge dispatch` 的复杂 Job 可以跳过统一校验 | 公开合同宣称失败关闭，实际存在旁路 | P1，版本阻断 |
| BG-05 | 持久进度没有控制器入口 | 即使 prepare 创建初始 `progress.json`，后续进度仍无正式同步命令 | “持久化进度”只能停留在初始占位状态 | P1，版本阻断 |
| BG-06 | 拒绝事件不可追溯 | Goal 工件错误在事件写入前抛出 | `background status` 不能解释 Job 为何没有启动 | P2 |
| BG-07 | 增量路线被整仓规模放大 | 增量知识和交付治理复用 project-wide 估算 | 小变化产生 phased Goal，放大宿主桥接成本 | P2 |

### 3.2 不是本次缺陷的行为

- 父任务先完成、后台治理独立失败或排队，是双通道设计，不回滚父任务。
- `queued_manual` 是可恢复状态，不等于后台 Job 已失败。
- 宿主能力不足时不得把复杂路线静默降级为 `background_direct`。
- `changed_paths=[]` 不创建增量 Job，保持 v1.6.0 当前实现。

## 4. 目标

v1.6.1 必须实现一个完整、可审计、失败关闭的宿主桥接：

```text
contract_ready
  → Harness prepare
  → 宿主建立 Goal / Plan
  → dispatched
  → running
  → Harness progress checkpoint(s)
  → Harness verify
  → terminal result
```

达到以下结果：

1. 宿主不再直接写 `plan.json`、`progress.json`、`job.json` 或 `events.jsonl`。
2. Harness 用正式 CLI 原子物化并维护 Goal 工件。
3. 所有新旧入口共享同一组复杂路线安全不变量。
4. 成功验收前，控制器能够证明全部工作包已完成。
5. 拒绝、重试、重基线和工件篡改都有脱敏、可复算事件。
6. 增量任务按实际变化面估算，bootstrap 继续按项目级规模估算。

## 5. 非目标

- 不新增 `prepared` Job 状态。
- 不修改父任务与后台任务双通道语义。
- 不删除 `knowledge job-status|dispatch|verify|retry` 兼容别名。
- 不允许静默路线降级。
- 不修改 `changed_paths=[]` 短路。
- 不修改 Git 同步、质量账本、任务包 v2 或知识 bootstrap 的业务合同。
- 不把应用内 Goal 会话编号、原始提示词、Plan 正文、异常正文或绝对宿主临时路径写入 Runtime 事件。
- 不在本方案阶段修改源码、测试、版本号或发布状态。

## 6. 核心产品合同

### 6.1 数据面与控制面分离

后台 Job 的写入权限拆成两个不可互换的平面：

| 平面 | 内容 | 写入者 | 范围合同 |
|---|---|---|---|
| 业务数据面 | `docs/**`、知识地图、ADR、Review、TODO、Changelog | 后台 Job | `allowed_write_scope` 与 `forbidden_write_scope` |
| Harness 控制面 | `job.json`、`plan.json`、`progress.json`、`events.jsonl`、锁与索引 | 仅 Harness CLI | 由 `background_*_root()` 解析的受管 Runtime 根目录 |

约束：

- `.git/**` 与 `.docs-harness/**` 不得加入业务 `allowed_write_scope`。
- 控制面豁免按“写入主体是 Harness CLI + 目标是已解析的受管 Runtime 文件”判断，不能用通配符放宽业务范围。
- 所有控制面路径必须由 `safe_target()`、`git_dir()`、`knowledge_job_dir()` 等现有安全路径函数解析，调用者不得传入输出路径。
- `create_background_job()` 增加显式守卫，拒绝业务写入范围覆盖 `.git/**`、`.docs-harness/**` 或实际 Runtime 根目录。

### 6.2 `background prepare`

新增命令：

```bash
python3 scripts/harness.py background prepare \
  --target . \
  --job-id <job-id> \
  --json
```

行为：

- `background_direct`：返回 `not_required`，不创建 Goal 工件。
- `background_goal|background_goal_phased`：从冻结的 `goal_contract`、`work_packages`、`job_id`、`idempotency_key` 确定性生成工件。
- 只允许 Job 处于 `contract_ready`；为 v1.6.0 在途 `dispatched` Job 保留一次补救入口。
- 成功后 Job 状态不变，写入 `job.goal_artifacts` 与 `prepared_at`，并追加 `prepared` 事件。
- 新工件固定写入 `artifact_revision=2` 与 `generated_by=docs-harness`，作为同一 Schema 下新旧格式的判别位。
- 重复调用仅在两个工件均属于当前 attempt、内容、绑定和指纹一致时返回 `already_prepared`。
- 已存在部分、无效或绑定冲突的工件时失败关闭，不静默覆盖。
- 普通 prepare 只补齐“两个工件均不存在”的 contract_ready/dispatched Job；`--repair` 专门处理部分、无效、绑定冲突或篡改工件，两者使用不同 reason code 和事件。
- v1.6.1 不接受 `--progress <file>`；初始进度必须由控制器生成，防止宿主在启动前声明虚假完成状态。

初始 `plan.json` 使用现有 `docs-harness/background-plan/v1`，补充确定性字段：

```json
{
  "schema_version": "docs-harness/background-plan/v1",
  "artifact_revision": 2,
  "generated_by": "docs-harness",
  "job_id": "<job-id>",
  "idempotency_key": "<key>",
  "objective": "<goal_contract.objective>",
  "work_packages": [
    {"id": "wp-01", "objective": "<frozen work package>"}
  ]
}
```

初始 `progress.json` 使用现有 `docs-harness/background-progress/v1`，补充尝试编号和确定性状态：

```json
{
  "schema_version": "docs-harness/background-progress/v1",
  "artifact_revision": 2,
  "generated_by": "docs-harness",
  "job_id": "<job-id>",
  "idempotency_key": "<key>",
  "attempt": 1,
  "work_package_states": [
    {"id": "wp-01", "status": "pending"}
  ],
  "completed_work_packages": [],
  "remaining_work_packages": ["wp-01"]
}
```

同一 Job、同一 `idempotency_key`、同一 attempt 必须生成同一工作包 ID 和相同语义内容。Plan 与 Progress 文件不写时间戳；`prepared_at` 只写入 `job.json` 和事件，因此 `file_fingerprint()` 可以直接用于幂等与篡改检测。

### 6.3 `background progress`

新增命令：

```bash
python3 scripts/harness.py background progress \
  --target . \
  --job-id <job-id> \
  --work-package-id <wp-id> \
  --work-package-status <in_progress|completed|blocked> \
  [--reason-code <bounded-code>] \
  --json
```

行为：

- 只允许 `background_goal|background_goal_phased`。
- 只允许 Job 处于 `running`；`dispatched` 只能表示宿主已接收但尚未开始执行，不能提前声明工作包进度。
- 工作包 ID 必须来自 `plan.json`；不得新增、删除或重命名工作包。
- 合法转换：`pending → in_progress|blocked`，`in_progress → completed|blocked`。
- 相同转换幂等；非法倒退返回 `invalid_background_progress_transition`。
- 每次更新在 Job 级控制锁内原子重写 `progress.json`，重新记录指纹并追加脱敏事件。
- `completed_work_packages` 和 `remaining_work_packages` 由 `work_package_states` 派生，调用者不能单独指定。
- `reason_code` 只接受受控、长度有界的标识符，不接受自由文本。

宿主调用 `update_plan` 后，必须用相同工作包 ID 调用 `background progress`。应用状态与 Harness 状态仍是两个平面，但桥接动作变为明确、可执行的宿主责任。

### 6.4 派发门禁

复杂路线设置两道门：

1. `contract_ready → dispatched`：必须已经 prepare，且 `job.goal_artifacts` 与当前文件指纹一致。
2. `dispatched → running`：重新校验 Schema、Job 绑定、工作包全集、进度全集、attempt 和指纹，防止 prepare 后被外部篡改。

缺失工件返回：

```json
{
  "code": "missing_background_goal_artifacts",
  "next_action": "prepare_background_goal",
  "next_command_argv": ["...", "background", "prepare", "--job-id", "<id>"]
}
```

不新增 `prepared` 状态。准备度由受校验的 `goal_artifacts` 字段表示，避免扩大状态迁移图和在途迁移成本。

### 6.5 成功验收门禁

`background verify` 对复杂路线增加最终进度校验：

- `updated|no_change`：所有工作包必须为 `completed`，`remaining_work_packages=[]`。
- `completed_with_finding`：工作包只能为 `completed|blocked`，不得仍有 `pending|in_progress`；必须提供现有 critical assessment，并在结果中返回 blocked 工作包 ID。
- 工件缺失、绑定不一致、进度指纹漂移或出现未知工作包时失败关闭。
- `background_direct` 保持现有验收行为。

这一步确保 `progress.json` 不只是启动占位文件，而是完成结论的组成证据。

### 6.6 `host_dispatch_contract`

复杂路线响应增加：

```json
{
  "required_preparation": "background_goal_artifacts",
  "control_plane_write_policy": "harness_cli_only",
  "prepare_argv": ["...", "background", "prepare", "--job-id", "<id>"],
  "progress_argv_template": [
    "...", "background", "progress", "--job-id", "<id>",
    "--work-package-id", "<wp-id>",
    "--work-package-status", "<status>"
  ],
  "dispatch_sequence": ["prepare", "create_host_goal", "dispatched", "running"],
  "manual_resume_argv": [
    ["...", "background", "retry", "--job-id", "<id>"],
    ["...", "background", "prepare", "--job-id", "<id>"],
    ["...", "background", "dispatch", "--job-id", "<id>", "--job-status", "dispatched"],
    ["...", "background", "dispatch", "--job-id", "<id>", "--job-status", "running"]
  ]
}
```

`manual_resume_argv` 保持 v1.6.0 的“argv 数组的数组”数据形状，只在中间插入 prepare，不把合同静默改成字符串步骤列表。

`background_direct` 返回 `required_preparation=null`，不要求宿主创建 Goal 工件。

### 6.7 兼容入口统一校验

保留 `knowledge job-status|dispatch|verify|retry`，继续返回弃用提示，但取消所有安全不变量豁免：

- 删除复杂路线依赖 `args.command == "background"` 才校验工件的条件。
- `legacy_direct_start` 只允许 `background_direct` 从 `contract_ready` 兼容进入 `running`。
- 复杂路线从 `contract_ready` 直接请求 `running` 时，无论入口均先返回 `invalid_background_job_transition`，并给出 `prepare → dispatched → running` 下一步；从 `dispatched` 请求 `running` 时再返回缺失、无效或篡改的 Goal 工件错误。
- `knowledge` 别名不新增 prepare/progress 子命令；错误响应明确引导到 `background prepare|progress`。

### 6.8 脱敏后台事件

新增统一 helper，例如 `append_background_event()`，替换后台状态机中的散装事件写入。

拒绝事件最小字段：

```json
{
  "event": "transition_rejected",
  "job_id": "<job-id>",
  "attempt": 1,
  "from_status": "contract_ready",
  "requested_status": "dispatched",
  "reason_code": "missing_background_goal_artifacts",
  "at": "<utc>"
}
```

隐私与有界要求：

- 不记录 Plan 正文、异常 message、用户任务正文、环境变量或宿主会话 ID。
- 不记录调用者提供的绝对路径；工件类型只用 `plan|progress` 枚举。
- 同一 attempt、同一状态转换、同一 reason code 的连续重复拒绝幂等去重，避免事件洪泛。
- 事件写入失败不得把原本的合同错误替换成不相关异常；返回中同时保留主 reason code 和受控的 `event_persisted=false`。

### 6.9 retry、rebase 与工件生命周期

| 来源状态/原因 | retry 的职责 | 下一步 prepare 的职责 |
|---|---|---|
| `queued_manual`，尚未执行 | 工件存在则归档；attempt 加一；清空 `job.goal_artifacts` | 为新 attempt 重新生成 Plan 与空 Progress |
| `needs_user_input` | 工件存在则归档；attempt 加一；清空引用 | 为新 attempt 重新生成两个工件 |
| `failed` | 工件存在则归档；attempt 加一；清空引用；修正终态摘要索引 | 为新 attempt 重新生成两个工件 |
| `needs_rebase` | 工件存在则归档；刷新基线；attempt 加一；清空引用 | 基于新基线重新生成两个工件 |
| 工件绑定/篡改错误 | 普通 prepare 不覆盖 | 显式 `prepare --repair` 先归档再生成当前 attempt 工件 |

实施约束：

- retry 只负责归档、attempt 推进、引用清理和基线刷新，不创建新 Plan 或 Progress；物化职责唯一属于 prepare。
- retry 不能继承上一 attempt 的“已完成”声明。
- 旧工件归档到 Job Runtime 内受管的 attempt 子目录，只保存工件本身和指纹，不复制业务文件。
- `job.goal_artifacts` 在需要重新 prepare 时清空；磁盘工件不得被误认为当前 attempt 有效。
- v1.6.1 明确提供 `background prepare --repair`；只能在 `contract_ready|dispatched` 使用，必须先归档旧工件、记录旧指纹和 repair 事件，不允许静默覆盖。
- 后台摘要索引按 `(job_id, attempt, status)` 幂等记录，而不是只按 `job_id` 去重；failed Job retry 后的新 attempt 终态必须能够追加新摘要，同时 prune 只依据最新 attempt 的终态判断。

## 7. 增量工作量评估修正

### 7.1 估算口径

`workload_estimate()` 增加明确的估算基础：

- `project_wide`：知识 bootstrap、全项目审查和明确要求全量 preserve-and-merge 的任务。
- `change_scoped`：知识增量同步与交付治理，输入实际 `changed_paths`、selected features、deliverable 数量和允许写入范围。

输入通道使用现有 `candidate` 合同的向后兼容扩展：内部增量调用点传入受控的 `estimate_basis=change_scoped`、`changed_paths`、selected features 和 deliverables；`background estimate --candidate <file>` 使用同一字段并经过路径、数量和长度校验。未声明 `estimate_basis` 时保持 `project_wide`。

响应增加：

```json
{
  "estimate_basis": "change_scoped",
  "project_scale_context": {
    "raw_score": 72,
    "scan_truncated": false
  },
  "change_scope_fingerprint": "sha256:..."
}
```

### 7.2 路由规则

- `changed_paths=[]` 仍在 verify 阶段提前短路，不进入估算。
- 单一功能、少量变化、无跨域依赖时，不因全仓文档数量达到阈值而强制 phased。
- 当前 `scan_truncated → background_goal_phased` 硬升级只保留给 `project_wide`；在 `change_scoped` 下只降低 confidence，只有实际变化面无法有界时才硬升级。
- bootstrap 继续使用 project-wide 路线，大仓库仍允许 `background_goal_phased`。
- 不修改 `source_fingerprint` 与 `background_idempotency_key` 的既有语义，避免在途 Job 重复创建。

## 8. 兼容与迁移

### 8.1 Schema

- `docs-harness/background-job/v2` 不升级。
- `docs-harness/background-plan/v1` 与 `background-progress/v1` 保持版本号；新格式用必需的 `artifact_revision=2` 与 `generated_by=docs-harness` 判别，避免在同一 Schema 下把旧字符串工作包误当成新格式强校验。
- 强校验只对 revision 2 工件生效；revision 缺失的旧工件只进入明确的在途兼容路径，不能用于新派发或新 attempt。
- `project-config/v4` 不升级。

### 8.2 在途 Job

- `contract_ready`：首次派发前必须运行 prepare。
- `dispatched` 且缺工件：允许运行 prepare 补齐，再进入 running。
- `running` 且 `job.goal_artifacts` 已证明是 v1.6.1 升级前绑定成功的旧工件：当前 attempt 走一次 legacy verify 豁免，不要求 `work_package_states`，但必须保留既有 Schema、Job 绑定、idempotency、范围和知识 ready 验收，并追加 `legacy_goal_artifacts_accepted` 事件；该 Job 不能调用新 progress 命令。
- 任何旧格式 Job 一旦 retry，必须归档旧工件并由 prepare 生成 revision 2 工件，不得再次使用 legacy verify 豁免。
- `queued_manual`：retry 后进入 contract_ready，并按新序列 prepare。
- 终态 Job：保持只读，不迁移、不重写。

迁移采用首次控制命令触发的惰性兼容，不要求 `project upgrade` 扫描并改写全部历史 Runtime。

## 9. 代码实施范围

### 9.1 `scripts/harness.py`

按以下顺序实施：

1. 新增控制面路径守卫与 Job 级控制锁；固定加锁顺序为 Job 控制锁在外、业务知识锁在内，反向释放，任何路径不得反序获取。

|---|---|---|
| Prepare | 复杂 Job 首次 prepare | 原子生成 revision 2 两个工件；绑定、attempt、工作包和指纹正确；状态不变 |

## 13. Codex 与 Claude Code 联合审查结论

### 13.1 共同结论

- prepare 必须发生在 `dispatched` 前。
- 不新增 `prepared` 状态。
- 控制面只能由 Harness CLI 写，不能把 `.git/docs-harness/**` 加入业务写入范围。
- prepare、别名旁路修复必须同批交付，否则新门禁仍可被旧入口绕过。
- retry 不能继承上一 attempt 的完成进度。
- 事件只保存有界原因码和状态，不保存正文、异常详情或宿主会话信息。
- bootstrap 保持 project-wide；增量 Job 才使用 change-scoped 估算。
- 不升级 background Job、Plan、Progress Schema 主版本。

### 13.2 合并时的调整

Claude Code 初稿建议 prepare 可接收 `--progress <file>`，并主要关注初始物化。Codex 复核后未采纳该部分，原因是：

1. 允许宿主输入初始 progress 会扩大伪造完成状态的入口。
2. 只有 prepare 而没有进度更新 CLI，宿主仍需直接写 Runtime，控制面所有权没有闭环。
3. 如果 verify 不校验最终进度，`progress.json` 仍只是形式工件。

因此最终方案增加 `background progress` 和成功验收进度门禁，并规定初始 Progress 只能由 Harness 生成。

### 13.3 Claude Code 终审后的闭环

Claude Code 对合并稿再次只读终审，提出的新旧工件判别、在途 running 兼容、retry/prepare 职责、`manual_resume_argv` 数据形状四个阻断项已全部写入当前方案：

- revision 2 判别位与 legacy verify 一次性豁免；
- retry 只归档、推进 attempt 和清引用，prepare 独占物化职责；
- `manual_resume_argv` 保持 argv 数组的数组；
- progress 仅允许 running，repair 明确纳入，摘要索引按 attempt 记录；
- alias 的错误码顺序、文件指纹口径、锁顺序和 change-scoped 输入通道已经定死。

因此当前方案不存在已知的实现前合同阻断项；真正完成仍以实施后的源码、真实宿主和下游证据为准。

## 14. 实施顺序与停止条件

### 阶段 A：控制面闭环

实现路径守卫、Job 级控制锁、prepare、progress、事件 helper 和工件强校验。

停止条件：无法在不扩大业务写入范围的前提下原子写入 Git/非 Git Runtime。

### 阶段 B：状态机与兼容入口

前移 dispatched 门禁，统一 background/knowledge 校验，增加 verify 进度门禁与 retry/rebase 生命周期。

停止条件：任何兼容路径仍可绕过 Goal 工件或进度门禁。

### 阶段 C：增量路由

引入 change-scoped 估算并保留 project-scale context、幂等键和 bootstrap 路线。

停止条件：路由修正导致现有 Job 幂等键变化或 bootstrap 被误降级。

### 阶段 D：合同、测试与版本

补齐测试，运行完整验证，同步公共合同和 `1.6.1` 版本真源。

停止条件：任一版本真源不一致、测试失败、公共示例仍缺少 prepare/progress，或出现超出本方案的文件变化。

## 15. 最终成功标准

v1.6.1 只有同时满足以下条件才可进入交付评估：

1. 复杂后台 Job 无需宿主直接写 Harness Runtime。
2. `host_dispatch_contract` 给出完整、可执行的 prepare、dispatch、progress、verify 路径。
3. 所有入口共享同一失败关闭安全不变量。
4. 成功结果能够证明工作包进度完成，而不是只证明两个 JSON 文件存在。
5. 拒绝与恢复过程可通过脱敏事件复算。
6. 小增量不会仅因整仓规模被无条件提升为 phased。
7. v1.6.0 的零变化短路和父任务双通道语义无回归。
8. 源码、真实宿主、下游安装与 Git 交付分别报告证据，不互相替代。

下一步唯一动作：另行授权真实宿主验收，在一个支持 Goal/Plan 的宿主中按 prepare → 创建宿主 Goal/Plan → dispatched → running → progress → verify 执行复杂 Job；源码、下游或交付范围若扩大，先重新准入。
