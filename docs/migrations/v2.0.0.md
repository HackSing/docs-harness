# Docs Harness 2.0.0 单向迁移指南

## 迁移目标

2.0.0 不是 1.x 的兼容模式，而是一次文档系统换代。所有 2.0.0 之前的项目升级后统一使用以下合同：

- Codex 默认直接完成用户任务；
- 缺少关键项目事实时才使用只读 `knowledge query`；
- 复杂、跨模块、高风险或用户明确要求时才选择方案模板；
- 验收围绕真实功能流程，不再运行 Harness Gate、Evidence、旧 Verify 或 Readmission；
- 旧规则、知识 bootstrap、后台治理 Job 和任务 Runtime 不再保留可激活能力。

目标不是“让旧流程默认关闭”，而是让升级后的项目里只剩一个明确的 2.0.0 文档系统。

## 升级原则

升级遵守四条数据边界：

1. **受管旧工件清理**：能通过安装指纹、Schema 或受管标记证明属于 Docs Harness 的旧工件删除或剥离。
2. **项目内容保留**：业务文档、ADR、TODO、方案、代码和用户修改不因路径位于 `docs/` 而被删除。
3. **归属不明不猜**：指纹不匹配、额外文件、符号链接或标记损坏时不自动覆盖；预览列出，应用失败关闭或保留脱钩。
4. **先预览再应用**：`upgrade` 默认只读；只有显式 `--apply` 才写入和清理。

## 第一步：预览

```bash
python3 <docs-harness-2.0.0-source>/scripts/harness.py project upgrade --target <project> --json
```

预览必须返回：

- `from_version` 与 `to_version=2.0.0`；
- 将创建、更新或删除的路径；
- `legacy_document_cleanup.remove_files`；
- `legacy_document_cleanup.remove_directories`；
- `legacy_document_cleanup.strip_managed_blocks`；
- `legacy_document_cleanup.preserved_paths`；
- `legacy_document_cleanup.conflicts`；
- `write_performed=false`。

当 `apply_completion_possible=false` 时不得应用。应先处理预览中的不安全路径或安装冲突。

## 第二步：应用

```bash
python3 <docs-harness-2.0.0-source>/scripts/harness.py project upgrade --target <project> --apply --json
```

这里的控制器必须来自新取得的 2.0.0 来源包。目标项目里原有的旧 scripts/harness.py 不具备 2.0.0 单向迁移能力，不能作为升级入口。

应用会安装：

- direct-first 的 `AGENTS.md` 受管区块；
-只负责转发 `AGENTS.md` 的 `CLAUDE.md` 受管区块；
- 2.0.0 `scripts/harness.py`；
- `plan-templates/`；
- `docs-harness/project-config/v6` 配置。

配置只记录直接模式、按需知识、方案模板指纹和迁移摘要，不再包含：

- `rules_root`；
- `installed_rule_fingerprints`；
- `gate_path_rules`；
- `verification`；
- `background_governance`；
- 任何可以重新开启旧任务控制的 opt-in。

## 会自动清理的旧工件

自动清理必须有机器可验证所有权。

| 旧工件 | 清理条件 | 2.0.0 动作 |
|---|---|---|
| `.docs-harness/harness-home/rules/*.md` | 文件名和 SHA-256 与旧配置 `installed_rule_fingerprints` 一致 | 删除文件；目录为空后删除目录 |
| `docs/knowledge-map.json` | Schema 以 `docs-harness/knowledge-map/` 开头 | 删除旧控制地图，保留其引用的项目正文 |
| `docs/INDEX.md`、`docs/modules/INDEX.md` 的版本区块 | 存在一组完整 `docs-harness:managed-version` 标记 | 只移除受管区块，保留其余正文 |
| `runs/` | 位于 Harness Runtime 根下且为常规目录 | 删除旧任务状态 |
| `knowledge/`、`knowledge-jobs/`、`task-inputs/` | 位于 Harness Runtime 根下且为常规目录 | 删除旧知识状态、Job 和任务输入暂存 |
| `background/` | 位于 Harness Runtime 根下且为常规目录 | 删除旧后台治理状态 |

Git 项目的 Runtime 根位于实际 Git 元数据目录下的 `docs-harness/`；非 Git 项目位于项目内 `.docs-harness/`。迁移不会用字面 `.git/` 猜路径，也不会删除 2.0.0 的 `v2/` 验收记录。

## 必须保留的项目内容

以下内容不是旧文档系统缓存，升级不会自动删除：

- `docs/features/**`、`docs/shared/**` 和其他项目知识正文；
- `docs/todo.md`、CHANGELOG、ADR、reviews、architecture、测试文档和用户方案；
- `.qoder/repowiki/**` 外部知识源；
- 质量账本 `quality-ledger/`；
- `AGENTS.md`、`CLAUDE.md` 受管标记之外的用户正文；
- 已修改或没有旧安装指纹的规则文件；
- 用户自建或已修改的方案模板。

已修改或无归属规则会被保留，但不会写入 v6 配置，也不会再被控制器加载。它们会进入 `migration.preserved_paths`，由项目所有者决定后续归档或删除。

## 失败关闭条件

以下情况在任何安装写入前停止：

- 旧规则根或 Runtime 路径是符号链接；
- 旧规则目录出现嵌套文件、额外符号链接或不安全类型；
- 受管版本标记缺一端、重复或顺序损坏；
- `scripts/harness.py` 或方案模板存在无法证明归属的覆盖冲突；
- Git 忽略 2.0.0 必需安装文件。

升级不会为了“完成迁移”而覆盖项目文件或跟随符号链接到项目外部。

## 旧命令已经删除

2.0.0 不再提供旧流程运行能力或兼容入口：

- `run`、`context`、`progress`、`verify`、`task`、`background` 和 `authorization` 不属于当前 CLI；
- `--legacy-opt-in` 已删除，不能恢复 1.x 入口；
- 旧命令对应的 Gate、Receipt、Verify、Readmission 和后台 Job 运行实现不进入 2.0.0 控制器；
- 旧任务状态不会阻断 Codex 直接执行，也不能被 2.0.0 继续推进。

如果业务仍依赖 1.x 状态机，应在升级前完成或导出必要业务信息。2.0.0 不以兼容旧状态作为产品目标。

## 升级后的使用方式

按需查询项目知识：

```bash
python3 scripts/harness.py knowledge query --target . \
  --query "需要确认的项目事实" --json
```

选择复杂任务方案模板：

```bash
python3 scripts/harness.py plan select --target . \
  --complexity complex --surface backend_service --json
```

记录真实验收层级：

```bash
python3 scripts/harness.py acceptance record --target . \
  --input acceptance.json --json
```

知识、方案和验收三项能力彼此独立；不使用时不会创建任务控制状态。

## 回滚边界

2.0.0 不提供“重新开启 1.x”的兼容回滚。若升级应用失败，应使用升级预览、工作区差异和版本控制恢复本次实际修改的受管文件。降级到旧软件包属于独立版本恢复，不是 2.0.0 运行模式。

无论是否回滚，都不得删除项目知识正文、业务代码、用户方案、ADR 或归属不明文件。

## 迁移验收

至少验证：

```bash
python3 scripts/harness.py project diff --target <project> --json
python3 scripts/harness.py project check --target <project> --json
```

完成标准：

- `project-config/v6` 生效且不存在旧配置键；
- `project diff` 没有待处理受管变化；
- `project check` 返回 `empty_rules_legal=true`、`legacy_rules_required=false`；
- 指纹归属明确的旧规则、旧知识地图、受管版本区块和旧 Runtime 已清理；
- 项目文档和用户修改仍在；
- 旧命令和 `--legacy-opt-in` 不存在；
- 重复执行 upgrade 不产生新变化。

源码测试通过只证明当前仓库实现，不等于 npm 已发布、下游项目已升级、ZBuddy 已安装或用户已经验收。
