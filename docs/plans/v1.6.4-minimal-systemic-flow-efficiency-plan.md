## 2. 执行摘要

`v1.6.3` 已解决验证命令新建常见临时副产物被误判为交付写入的问题，并允许普通新增 Gate 在合同不变时增量准入和继承同轮证据。但当前状态机仍以整个 `package_fingerprint` 作为过多对象的共同失效边界，导致以下循环继续存在：

1. 第一份计划先声明范围，Harness 再根据范围发现安全、测试或架构 Gate，计划合同随后发生变化，宿主被迫重新加载上下文并重新提交计划。
2. plan 与 action 阶段经常引用完全相同的规则和项目事实，但收据按 stage 隔离，导致正文重复加载或至少产生无业务价值的控制往返。
3. 计划、授权和证据依赖调用者临时文件持续存在且字节不变；文件清理、改名或任务包修订可能让已验证事实失效。
4. 每次 `verify` 都重新执行全部验证命令；某个命令失败、缺少另一类证据或产生阻断写入时，已经通过的昂贵命令仍会重跑。
5. 可补证、可重读、可重试和真正需要重新准入的情况没有充分分层，多个可恢复状态被统一映射为完整重新准入。
6. 失败的 verify 没有形成完整事件，系统无法准确统计验证轮次和循环原因。

本方案不通过放松安全 Gate 解决效率问题，而是采用一个最小系统性原则：

> 只有发生变化的合同分段失效；安全边界不变的内容、计划、授权、上下文和验证收据继续复用。

目标主流程为：

```text
任务意图与候选范围
  ↓
范围绑定 + Gate 编译
  ↓
最终计划合同（只生成一次）
  ↓
计划冻结 + 必要授权
  ↓
内容寻址的上下文确认
  ↓
执行
  ↓
逐命令、可复用的验证收据
  ↓
补证 / 重读 / 重试 / 增量准入 / 完整重新准入
  ↓
一次性完成回执
```

## 3. 审查证据与问题边界

### 3.1 真实任务样本

审查 `D:\Project\ZBuddy\.git\docs-harness\runs` 时，共发现 162 个任务。最近 50 个任务中：

- 21 个任务的 package revision 大于 1；
- 发生 17 次 `scope_bound_readmission`；
- 发生 13 次其他 `readmission`；
- 发生 68 次上下文调用，其中 plan 44 次、action 24 次；
- 最近 50 个任务的 plan/action context schedule 全部相同；已有 15 个任务同时调用两个阶段，产生 20 次 action 阶段重复内容调用；
- 发现 5 个相同任务快照的额外任务；全部 162 个任务中共有 30 个额外重复任务。

上述 Runtime 来自已安装的 `v1.5.0`，不能替代新版本验收，但它证明了范围绑定、上下文、任务重复和后台收尾造成的真实操作成本。

### 3.2 安全与测试 Gate 场景

“正式计划冻结范围后触发安全与测试 Gate 重编译”包含两类不同语义：

- `security-sensitive` 合理增加 `安全边界`、`负向路径`、`docs/security.md` 和 `security_acceptance`；
- `testing-acceptance` 不增加计划字段，只增加 `docs/testing.md` 和 `test_result`。

Gate 收紧本身是预期行为。问题在于当前流程在 Gate 编译完成前就把第一份含范围文档称为正式计划，形成以下循环：

```text
正式计划 → 冻结范围 → 编译新 Gate → 正式计划合同变化 → 重写正式计划
```

正确语义应为：

```text
计划草稿中的范围提案 → 编译 Gate → 输出最终计划合同 → 正式计划一次冻结
```

### 3.3 当前源码仍存在的关键缺口

1. `recompile_package_from_plan_scope()` 无条件生成下一 revision，并要求 `scope_bound_context_reload`；第一次提交的计划没有在新 Gate 合同下被重新校验和采用。
2. context receipt 的正文复用要求 stage 相同，plan 已加载内容不能直接满足 action 内容交付。
3. `plan_is_current()`、`authorization_is_current()` 和 evidence reuse 都依赖外部 `source_ref` 文件仍存在。
4. 增量 Gate 重编译会复制 compiled authorization 状态，但不会给新 package fingerprint 生成有效授权收据；若还需要加载增量上下文，下一次 verify 可能再次因授权失效进入完整重新准入。
5. 验证命令使用批次级工作区前后快照；阻断写入会翻转批次中所有已通过命令，而且下一次 verify 仍执行全部命令。
6. `unattributed_drift_overlap`、`read_set_drift`、任意 Git postcheck 失败等情况缺少针对性恢复动作。
7. 失败 verify 不写完整 verification attempt 事件；`readmission_count` 也未统计增量 Gate readmission。
8. 文档合同声明 `changed_paths=[]` 时应 `no_write_no_sync`，但治理分支仍可能创建 background governance Job。

## 4. 产品目标

1. 范围绑定后先完成 Gate 编译，再冻结最终计划；同一正式计划不因预期的首次范围编译重复生成。
2. 只要求补充新 Gate 真正新增的计划字段，不要求重交未变化字段。
3. 同一任务、同一目标、同一 compiler contract 下，相同内容指纹的规则或项目事实正文只交付一次；不同 stage 仍各自保留确认收据。
4. 已验证的计划、授权和证据由 Harness 摄取到受管 Runtime，不因调用者临时文件清理而失效。
5. 验证命令逐项执行、逐项快照、逐项持久化；输入未变化时不重复执行已通过命令。
6. 将补证、重读、重试、增量准入和完整重新准入明确分层。
7. 只有范围、路线、授权合同、规则语义或高风险边界变化时才完整重新准入。
8. 每次 verify 尝试均可由结构化事件复算，能准确定位重复工作来源。
9. 无业务变化时不创建知识或治理后台 Job。
10. 新机制必须在源码、临时项目、真实下游安装副本和目标项目 Runtime 四个层级分别验收。

## 5. 非目标与不可放松边界

- 不降低 `security-sensitive`、`destructive-data`、`release-external`、架构兼容、前端设计等高风险 Gate 的识别要求。
- 不允许计划补丁改变已冻结 scope、路线、授权动作、外部目标或工作包而绕过完整重新准入。
- 不跨任务或跨目标复用上下文、授权、证据或验证命令收据。
- 不把已有同名临时文件的修改或删除视为可忽略副产物。
- 不允许缺少可信生产者的报告型证据满足安全、发布、恢复或不可逆操作验收。
- 不自动提交、推送、发布、安装、修改 `.gitignore` 或清理用户文件。
- 不重写后台治理整体架构；只修复无变化派发和 change-scoped 指纹边界。

## 6. 最小合同分段模型

`package_fingerprint` 继续作为完整任务包审计指纹，但不再是所有对象唯一的复用键。新增或明确以下分段指纹：

| 指纹 | 绑定内容 | 主要消费者 |
|---|---|---|
| `scope_contract_fingerprint` | read/write/git/external scope、动作、路线、工作包 | 计划、漂移归因 |
| `plan_contract_fingerprint` | plan fields、Gate、阻断交付物、成功标准 | 正式计划 |
| `authorization_contract_fingerprint` | 授权动作、授权范围、Git 范围、外部目标 | 授权收据 |
| `context_content_fingerprint` | 单条规则或项目事实正文 | 跨阶段内容复用 |
| `context_set_fingerprint` | 某阶段所需内容集合 | 阶段确认收据 |
| `verification_input_fingerprint` | 非 volatile 工作区快照、命令、cwd、相关工具链标识 | 验证命令收据 |

完整 package revision 变化时，控制器计算 `contract_delta`：

```json
{
  "schema_version": "docs-harness/contract-delta/v1",
  "from_package_fingerprint": "sha256:...",
  "to_package_fingerprint": "sha256:...",
  "added_gates": ["security-sensitive", "testing-acceptance"],
  "added_plan_fields": ["安全边界", "负向路径"],
  "added_context_refs": ["docs/security.md", "docs/testing.md"],
  "added_evidence_types": ["security_acceptance", "test_result"],
  "scope_changed": false,
  "route_changed": false,
  "authorization_contract_changed": false,
  "work_packages_changed": false,
  "blocking_deliverables_changed": false,
  "disposition": "plan_amendment"
}
```

`disposition` 只能由控制器生成，取值：

```text
no_change
context_only
plan_amendment
evidence_only
incremental_admission
full_readmission
```

## 7. 范围绑定与正式计划一次冻结

### 7.1 兼容现有 CLI 的最小改法

不新增必需命令。继续允许第一份 `--plan` 包含执行范围，但在范围尚未绑定时把它解释为“计划草稿 + 范围提案”：

1. 读取计划草稿并取得 requested scope。
2. 在同一事务中基于 scope 重编译 Gate、规则、计划字段、证据和上下文合同。
3. 用新任务包的最终 `plan_fields` 重新校验刚提交的计划草稿。
4. 若计划已经满足最终字段，直接摄取并冻结为正式计划，不要求再次提交。
5. 若只缺新增字段，保存已有计划内容并返回 `complete_plan_delta`，只列出缺失字段。
6. 宿主提交补丁后，控制器合并、校验并冻结最终计划；不得要求重新生成未变化正文。
7. 只有 scope、路线、授权合同、工作包或阻断交付物再次变化时返回 `full_readmission`。

### 7.2 安全与测试 Gate 的预期响应

范围提案首次触发安全和测试 Gate 时，响应应为：

```json
{
  "result": "补充计划",
  "reason_code": "scope_gate_plan_amendment_required",
  "added_gates": ["security-sensitive", "testing-acceptance"],
  "missing_plan_fields": ["安全边界", "负向路径"],
  "added_evidence_types": ["security_acceptance", "test_result"],
  "plan_regeneration_required": false,
  "source_execution_allowed": false,
  "next_action": "complete_plan_delta"
}
```

`testing-acceptance` 单独新增时，因其没有计划字段，不得触发计划补写；它只更新上下文和 completion manifest。

### 7.3 审计要求

- package revision 可以增加，用于记录 Gate 编译历史；revision 增加不等于必须重做全部宿主动作。
- `package-history` 保存旧任务包和 `contract_delta`。
- 在正式计划冻结前，业务源码仍不得修改。
- 计划补丁必须绑定原计划 artifact fingerprint、目标 plan contract fingerprint 和当前 task ID。

## 8. 上下文正文跨阶段复用

阶段确认和正文交付拆分：

- `content-delivery receipt` 证明某条内容正文已在当前 task/target/compiler contract 下交付；
- `stage acknowledgement receipt` 证明 plan/action/work-package 阶段已确认其所需内容集合。

复用规则：

1. task、target、compiler contract 和内容指纹相同：正文不重复交付。
2. stage 不同：生成新的阶段确认收据，但只返回该阶段尚未交付的正文。
3. 内容集合新增：只返回新增内容，并标记 `context_delta=true`。
4. 内容正文变化或 compiler contract 变化：重新交付对应内容。
5. 跨 task、跨 target：禁止复用。

在安全与测试 Gate 场景中，第二次上下文响应只应包含新增加的安全规则、测试规则、`docs/security.md` 和 `docs/testing.md`；原架构、产品或开发内容不得重传。

## 9. 受管工件摄取

### 9.1 统一 artifact store

在任务 Runtime 下新增控制器所有的不可变工件目录：

```text
<task-state>/artifacts/
  plans/
  authorizations/
  evidence/
  verification/
```

所有文件型输入遵循同一过程：

1. 有界读取并完成 Schema、编码、大小、目标和任务绑定校验。
2. 计算原始来源指纹和规范化对象指纹。
3. 原子写入受管 artifact store。
4. Runtime 索引引用受管副本；调用者路径仅记录为脱敏 provenance。
5. 后续有效性判断读取受管副本，不要求调用者临时文件继续存在。

### 9.2 计划

- 正式计划冻结后引用受管副本。
- JSON 计划使用 canonical JSON 计算语义指纹；Markdown 计划保存不可变字节副本，并额外记录解析后的受控字段摘要。
- 调用者后续修改原文件不自动改变已冻结计划；显式重新提交才触发计划变更流程。

### 9.3 授权

- 新授权收据同时绑定 package fingerprint 和 `authorization_contract_fingerprint`。
- package revision 变化但授权合同完全相同时，控制器可以生成 `authorization-adoption/v1`，引用原授权、原 package 和新 package。
- 授权动作、任何授权范围、Git scope、外部目标或有效期变化时禁止继承。
- 在 adoption 合同实现前，带授权要求的任务不得走会要求下一轮 verify 的增量 Gate 路径；必须一次性完成或保守返回完整重新准入，避免先增量后再次失败。

### 9.4 证据

- 首次 `verify --evidence` 校验通过后立即摄取到 Runtime。
- package revision 兼容继承使用独立 `evidence-adoption/v1` 包装记录，不直接把来源文件中的旧 package fingerprint 伪装为新值。
- adoption 记录必须保存原 package、新 package、contract delta、原证据 ID、来源指纹和采用原因。
- 删除调用者临时证据文件不得使已摄取证据失效。

## 10. 验证命令逐项收据与复用

### 10.1 执行模型

每条验证命令独立执行以下流程：

```text
计算 verification_input_fingerprint
  ↓
查找可复用通过收据
  ├─ 命中：记录 cache hit，不执行命令
  └─ 未命中：命令前快照 → 执行 → 命令后快照 → 分类写入 → 持久化收据
```

不再用一组命令共享的单一前后快照给所有命令归因。

### 10.2 收据键

可复用收据至少绑定：

```text
task_id
target_identity
verification command argv digest
cwd
verification_input_fingerprint
declared produces
relevant contract fingerprint
producer capability
ttl
```

`verification_input_fingerprint` 初期使用排除 Harness Runtime 和允许 volatile 新建项后的完整工作区快照，保证实现简单且保守。以后只有在命令声明可信 read-set 时才允许缩小输入集合。

### 10.3 重跑规则

- 命令通过，但缺另一类人工证据：下一次 verify 复用命令收据。
- 多条命令中一条失败：只重跑失败命令。
- 一条命令产生阻断写入：只把该命令标记为 `verification_command_workspace_write`。
- 工作区输入指纹变化：相关命令收据失效并重跑。
- package revision 变化但命令、输入和相关合同分段不变：通过 adoption 记录复用。
- 安全或发布证据仍必须满足可信生产者要求，普通命令缓存不能提升证据等级。

## 11. Verify 结果分级

将当前“补证或完整重新准入”二分法调整为五级：

| 分类 | 典型原因 | package revision | 推荐下一步 |
|---|---|---:|---|
| `provide_evidence` | 缺少类型化证据、允许范围内缺 write-set 归因 | 不变 | 补充收据 |
| `refresh_evidence` | read-set 内容变化、证据过期 | 不变 | 重读或重做相关结论 |
| `retry_verification` | 命令失败、可重试 Git/网络检查 | 不变 | 只重试失败检查 |
| `incremental_admission` | 普通新增 Gate，路线/范围/授权/计划合同不变 | 增加 | 加载 delta 后继续 |
| `full_readmission` | 越界写入、高风险 Gate、规则变化、授权合同变化、远端目标/ref 漂移 | 增加 | 重新准入 |

### 11.1 具体原因码映射

| 当前原因 | 新处理 |
|---|---|
| `unattributed_drift_overlap` 且全部路径在 write scope、无高风险 Gate | `provide_evidence`，要求补归因收据 |
| `read_set_drift` | `refresh_evidence`，只失效引用该路径的证据 |
| 验证命令非零退出 | `retry_verification` |
| Git 工具暂不可用、网络读取失败 | `retry_verification` |
| `git_remote_drift`、ref 越界、HEAD/目标不一致 | `full_readmission` |
| 普通 `testing-acceptance|code-edit|document-edit` 新增且合同稳定 | `incremental_admission` |
| `security-sensitive|destructive-data|release-external` 新增 | `full_readmission`；首次 scope 编译阶段则进入最终计划合同，不视为执行后失败 |
| active rule content fingerprint 变化 | `full_readmission` |

## 12. Gate 前置与路径识别

### 12.1 前置时机

Gate 推断按以下时机执行：

1. 原始任务和显式 facts；
2. 范围提案首次绑定；
3. 正式计划冻结前的候选路径；
4. 执行后实际 task write-set；
5. verify 只处理真正无法前置的差异。

范围提案绑定产生的 Gate 属于“计划合同编译”，不应被描述为 verify 末端新增风险。

### 12.2 路径分词

路径 Gate 推断统一对目录段和文件 stem 做以下规范化：

- `/`、`.`、`_`、`-` 分隔；
- camelCase 和 PascalCase 分词；
- 保留完整 token 边界，避免 `authors` 命中 `auth`、`rapid` 命中 `api`；
- 测试文件继续识别 `*.test.*`、`*.spec.*`、`*_test.*` 和受控中文测试描述。

新增回归覆盖 `authService.ts`、`permissionStore.ts`、`apiClient.ts`、`schemaVersion.ts`，同时证明 `authors.ts`、`rapid.ts` 不误命中。

## 13. 任务幂等与失败遥测

### 13.1 活动任务幂等

首次 `run` 计算：

```text
active_task_key = sha256(
  target_identity
  + task_snapshot_ref
  + normalized facts fingerprint
  + initial workspace snapshot fingerprint
)
```

存在相同 key 的非终态任务时，默认返回现有 task ID、当前状态和下一步，不创建第二个任务。显式 `--new-task` 才创建独立任务。

已完成、取消、失败终态或初始工作区不同的任务不复用。

### 13.2 每次 verify 都记事件

每次 verify 入口最终必须写入一个有界事件，无论结果是完成、补证、重试、增量准入还是完整重新准入：

```json
{
  "event": "verification_attempt",
  "outcome_class": "retry_verification",
  "reason_codes": ["verification_command_failed"],
  "package_revision": 2,
  "command_executed_count": 1,
  "command_cache_hit_count": 3,
  "context_full_load_count": 1,
  "context_delta_load_count": 1,
  "evidence_regeneration_required": false
}
```

事件不得保存命令原始输出、计划正文、证据正文、环境变量或凭证。

`readmission_count` 必须统计：

```text
readmission
scope_bound_readmission
incremental_gate_readmission
```

## 14. 最小后台收尾修复

1. `changed_paths=[]` 时，知识增量和 delivery governance 均返回 `no_write_no_sync`，不得创建 Job。
2. change-scoped workload estimate 可以保留 project-wide scale context，但其去重和 `source_fingerprint` 必须仅绑定 changed paths、selected features、deliverables、解析后的写入范围及其相关文件指纹。
3. 无关项目文件变化不得改变 change-scoped Job 的 idempotency key。
4. 本方案不改变 `background_direct|background_goal|background_goal_phased` 的安全门禁、计划工件和进度验收。

## 16. 实施顺序

### 阶段一：关闭现有循环漏洞

内容：

- 修复“增量 Gate + 授权 + delta context”下一轮 verify 再次失效的问题；
- 每次失败 verify 写入结构化事件；
- `readmission_count` 纳入增量 Gate；
- `changed_paths=[]` 不创建治理 Job；
- 增加安全与测试 Gate 范围绑定回归。

出口门槛：

- 带授权任务不会先进入增量路径再因旧 package fingerprint 被迫完整重走；
- Runtime 能准确复算所有 verify 尝试；
- 无业务变化任务不创建后台 Job。

### 阶段二：一次计划冻结与上下文去重

内容：

- 范围绑定后在同一事务中重新校验并采用计划；
- 实现 `contract_delta` 和 `complete_plan_delta`；
- 拆分内容交付与阶段确认收据；
- 测试 Gate 单独新增时不要求计划补写。

出口门槛：

- 首次 scope 触发安全与测试 Gate 时，只补 `安全边界|负向路径`；
- 原计划其他字段不重新生成；
- 正式计划只冻结一次；
- plan/action 相同内容正文只返回一次。

### 阶段三：工件摄取与验证命令复用

内容：

- 实现受管 artifact store；
- 计划、授权、证据改用受管副本；
- 实现 authorization/evidence adoption 记录；
- 验证命令逐项快照、逐项收据、输入指纹缓存。

出口门槛：

- 调用者临时文件删除后，已摄取计划、授权和证据继续有效；
- 补人工证据时不重跑已通过命令；
- 多命令中只重跑失败或输入失效的命令。

### 阶段四：失败分级、任务幂等和下游验收

内容：

- 完成 verify 五级结果映射；
- 实现 active task key；
- 优化 change-scoped 后台指纹；
- 完成源码、临时项目、真实安装和 Runtime 指标验收。

出口门槛：

- 可补证、可重读、可重试的问题不增加 package revision；
- 相同活动任务不会重复创建；
- 高风险变化仍完整重新准入；
- 下游安装脚本指纹与候选源包一致。

## 18. 必需回归矩阵

### 18.1 范围与计划

1. 无初始 scope 的计划草稿声明普通源码：Gate 编译后字段齐全，直接冻结，不重交。
2. scope 同时包含安全源码和测试文件：只补 `安全边界|负向路径`，测试 Gate 不增加计划字段。
3. 补丁修改 scope：完整重新准入。
4. scope 导致 route、授权或工作包变化：完整重新准入。
5. 正式计划冻结前不得修改产品源码。

### 18.2 上下文

1. plan/action schedule 完全相同：action 返回零正文但生成阶段确认收据。
2. 安全与测试 Gate 新增：只返回新内容。
3. 单条规则正文变化：只重新交付变化内容。
4. 跨 task/target/compiler contract：禁止复用。

### 18.3 授权与证据

1. package revision 变化但授权合同完全相同：受控 adoption 后继续。
2. 任一授权范围或外部目标变化：拒绝 adoption。
3. evidence 临时来源文件删除：受管副本继续有效。
4. 高风险证据仍要求 verified producer。
5. adoption 记录能追溯原 package 和来源证据。

### 18.4 验证命令

1. 验证命令通过但缺人工证据：第二次 verify 不重跑命令。
2. 三条命令中一条失败：只重跑一条。
3. 一条命令产生阻断写入：不翻转其他命令。
4. 新建 volatile 文件：通过并保持可见。
5. 修改或删除已有 volatile 同名文件：仍失败关闭。
6. 工作区输入变化：缓存失效并重跑。

### 18.5 结果分类

1. 允许范围内缺 write-set：补证，不重新准入。
2. read-set 漂移：只刷新相关证据。
3. Git 网络读取失败：重试。
4. Git 远端目标漂移或 ref 越界：完整重新准入。
5. 新安全、数据、发布 Gate：完整重新准入。
6. 普通 additive Gate 且合同稳定：增量准入。

### 18.6 幂等与后台

1. 相同 active task key：返回现有任务。
2. 初始工作区不同：创建新任务。
3. `changed_paths=[]`：零后台 Job。
4. change-scoped 无关文件变化：Job idempotency key 不变。

## 19. 量化验收指标

在固定基线任务集上同时记录旧流程和候选流程：

| 指标 | 验收目标 |
|---|---|
| scope 首次绑定后的完整计划重新生成次数 | `0` |
| 安全+测试 Gate 场景需要补充的计划字段 | 仅 `安全边界|负向路径` |
| 同一内容指纹正文交付次数 | 每 task/target/compiler contract 最多 `1` |
| package revision 兼容变化后的证据重新生成次数 | `0` |
| 输入未变化的通过验证命令执行次数 | `1` |
| 单命令失败导致其他命令重跑次数 | `0` |
| 失败 verify 事件覆盖率 | `100%` |
| 相同 active task key 的额外任务数 | `0` |
| `changed_paths=[]` 创建的后台 Job 数 | `0` |
| 高风险 Gate、授权合同或范围变化被降级放行 | `0` |

不以“平均减少百分比”代替原始计数；所有指标必须能从 Runtime 事件和收据复算。

## 20. 迁移、回滚与部署

1. 新任务使用新状态语义；现有活动任务不静默重写。
2. 旧任务继续按原合同完成，或显式迁移后重新准入。
3. 新增分段指纹和 adoption 对象必须由旧控制器失败关闭或只读忽略，不能按旧语义误用。
4. artifact store 写入失败时保持原索引不变，不产生半摄取状态。
5. 验证命令缓存可通过配置整体关闭；关闭后回退为逐命令执行，不回退为批次误归因。
6. 回滚前检查活动新版本任务；存在活动任务时阻断控制器降级。
7. 源码通过后，先升级临时项目并核对版本、配置和脚本指纹。
8. 下游项目升级需单独授权；升级后必须核对 `installed_script_fingerprint`、实际入口脚本哈希和运行任务事件版本。
9. 不能用 `D:\Project\docs-harness` 源码状态证明 `D:\Project\ZBuddy` 已获得新行为。

## 21. 风险与控制

| 风险 | 控制 |
|---|---|
| 分段指纹被用来跨风险合同复用 | 每种收据只接受明确的相关合同指纹；范围、路线、授权、高风险 Gate 变化失败关闭 |
| 计划补丁绕过完整计划审查 | 补丁只能填写控制器列出的缺失字段，禁止改变已冻结字段和 scope |
| 跨阶段上下文复用导致未确认规则 | 正文可复用，stage acknowledgement 必须单独生成 |
| 临时证据摄取后来源被替换 | 受管副本和来源指纹不可变；后续只信任受管副本 |
| 验证缓存复用陈旧结果 | 绑定完整非 volatile 工作区输入和 TTL；输入变化即失效 |
| Git 瞬时错误被误当成功 | 只改变恢复动作，不改变通过条件 |
| 普通 drift 被错误放行 | 缺归因时只允许补证，不自动计入 task write-set |
| 遥测泄漏敏感信息 | 只保存计数、受控原因码、指纹和有界路径 |

## 22. 完成定义

只有同时满足以下条件，才可以声明本方案完成：

1. 本文档的必需回归矩阵全部通过。
2. 当前源包 self-test 和 package 检查通过。
3. 临时项目完成 init/upgrade、准入、范围绑定、计划补丁、授权、证据、verify 和回滚窗口测试。

5. 至少一个真实宿主任务证明安全+测试 Gate 只补增量字段和上下文。
6. 至少一个昂贵多命令任务证明通过命令不会因补证而重跑。

## 23. 建议的第一实现批次

若只允许一个最小实现批次，优先完成以下四项：

1. 范围绑定后重新校验并采用原计划，新增 `complete_plan_delta`，取消整份计划重交。

受管 artifact store、任务幂等和后台 change-scoped 指纹随后实施，但其合同必须在第一批次中定稿，避免再次引入 package fingerprint 级联失效。
