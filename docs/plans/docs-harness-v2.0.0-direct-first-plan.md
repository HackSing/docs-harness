# Docs Harness v2.0.0：Codex 直接执行、按需知识与真实验收方案

> 状态：已实施-仅追溯（代码已是真源，2026-08-14 核对）

- 目标版本：`2.0.0`
- 文档状态：最终产品与实施方案；本地实现候选已完成，发布与下游验收未完成
- 决策日期：2026-08-09
- 当前源码基线：基于提交 `e0ca4fb` 的未提交工作区；`VERSION`、`package.json`、SKILL 和控制器已同步为 `2.0.0`
- 版本口径：本文中的 `2.0.0` 是目标重大版本；在源码、测试、包清单、版本真源、下游同步和真实验收全部完成前，不得宣称 2.0.0 已发布
- 核心方向：默认直跑、知识按需、方案按需、Codex 原生安全、真实功能验收

## 1. 文档定位

本文重新定义 Docs Harness 的产品职责和 Codex 项目任务流程，替代“所有任务都必须经过 Intent、Gate、Plan、Evidence、Verify、Readmission”的强制治理方向。

本次是重大版本设计，原因不是增加更多治理能力，而是改变默认行为：

- 1.x 默认把 Harness 作为任务准入和完成闭环；
- 2.0.0 默认不调用 Harness，Codex 直接理解、执行和验收任务；
- 项目知识、方案模板和验收记录拆成独立能力，只有确实需要时才启用；
- 任务级 Gate、动作 preflight、Harness 授权和 Host Adapter 全部移除，高风险动作直接使用 Codex 原生授权与沙箱；
- Verify 不再核对 Harness 自身合同，改为记录真实功能验收结果；
- Harness 不再建立任务级控制状态、授权收据和运行时遥测。

本文是 2.0.0 的产品真源和实施依据。此前的有效上下文密度、Gate、Verify 和 Host Adapter 方案只作为历史问题证据；其中 Gate、preflight、Host Adapter 和 usage metrics 路线已被明确否决，不再作为未来待接入能力。

## 2. 产品决策

### 2.1 最终决策

Docs Harness 2.0.0 不再管理 Codex 的全部工作过程。

默认任务流程是：

```text
用户提出任务
↓
Codex 直接理解任务
↓
按需加载项目知识或简洁方案
↓
Codex 执行任务
↓
运行能够直接覆盖本次变化的最小真实验收
↓
如实报告已验证、待用户验证和未验证内容
```

只有以下情况才启用 Harness 的独立辅助能力：

- Codex 缺少项目背景、架构或历史约束时，启用知识辅助；
- 任务复杂、跨模块或风险较高时，启用方案辅助；
- Codex 无法独立完成真实验收时，启动最小运行环境并交给用户确认。

删除、发布、推送、合并或外部写入等高风险动作不调用 Harness，直接遵循 Codex 原生授权、沙箱和用户确认机制。

### 2.2 为什么升级为 2.0.0

这不是兼容性小调整，而是默认产品合同变化：

- 默认从“必须准入”改为“无需 Harness”；
- `Gate`、Harness 动作 preflight 和第二套授权系统从新流程中移除；
- `Verify` 从控制合同核验改为真实行为验收；
- `Plan` 从通用填表改为复杂任务的最小方案；
- `Context` 从自动注入改为按需检索；
- 旧的 Run/Verify/Readmission、规则与后台 Job 进入单向清理状态，不保留可激活兼容能力。

因此使用重大版本号 `2.0.0`，避免宿主和下游项目误以为旧调用方式、响应结构和默认行为保持不变。

## 3. 当前问题与决策依据

### 3.1 现有系统问题

现有审查已经确认：问题不只是知识库注入过长，而是控制面和模型执行面混在一起。

2026-08-08 ZBuddy 的 53 个完成任务中：

- 分配了 79 个 Gate；
- 发生了 75 次 Verify；
- 75 次 Verify 中有 70 次没有执行验证命令；
- 错误 Gate 会继续派生规则、Plan 字段、证据和重准入；
- Run、Verify 和重准入会将大量控制器状态重新送入模型上下文；
- 只读任务出现过度治理，构建、合并和本地写入任务又出现漏控。

这些数据可以证明额外流程、误判和注意力干扰风险，不能单独证明模型内在能力下降百分比。

### 3.2 用户体验决策

用户在 ZBuddy 中明确关闭 Harness 后，直接观察到 Codex 的任务体验明显改善。对于以用户个人和本地项目生产力为核心的产品，这一体验已经足以决定默认行为，不要求用户继续承担 A/B 证明成本。

因此：

- 2.0.0 默认关闭强制 Harness 流程；
- 不再通过实验决定是否允许用户直接执行；
- 未来任何辅助能力如果希望扩大默认启用范围，必须由该能力自己证明增量价值；
- 不因为历史投入、既有代码或治理完整性继续维持低效主流程。

### 3.3 保留的原始价值

最初产品目标仍然成立：

1. 为项目提供可靠、按需的知识库；
2. 为复杂任务提供简洁、稳定的方案模板；
3. 帮助 Codex 或用户完成真实功能验收。

高风险保护仍是完整 Codex 任务流程的必要能力，但由 Codex 原生权限与沙箱承担，不再重复建设在 Docs Harness 中。2.0.0 保留上述三项 Harness 价值，移除把它们绑定成一条强制治理流水线的设计。

## 4. 产品目标与非目标

### 4.1 核心目标

1. 普通任务不调用 Harness，也能立即开始执行；
2. 项目知识只在缺少关键事实时加载，并保持短、准、可追溯；
3. 方案只服务复杂任务执行，不要求简单任务填表；
4. 高风险动作沿用 Codex 原生安全能力，Harness 不增加第二次判断和授权；
5. 验收直接覆盖用户要求的行为，不用 Harness 合同闭环代替功能正确性；
6. Codex 能自动完成的真实流程由 Codex执行；
7. Codex 无法独立验收时，为用户准备最低成本的运行环境和操作步骤；
8. 所有完成声明明确区分源码、测试、本地运行、包、安装和用户验收层；
9. Harness 不建立运行时 usage 遥测和任务级控制记录；
10. 任何辅助能力都可以独立关闭，不影响 Codex 基本工作。

### 4.2 非目标

2.0.0 不追求：

- 为所有任务建立完整任务包；
- 为普通问答、只读检查和小修改生成 Plan；
- 通过增加 Gate、Evidence 或 Receipt 数量证明治理完整；
- 用测试数量代替功能验收质量；
- 用固定 Token 阈值代替上下文相关性；
- 让模型理解 Harness 的全部内部状态；
- 自动更新项目知识库或长期记忆；
- 代替 Codex 宿主的权限、安全沙箱和用户授权机制；
- 在没有包、安装或用户验收证据时宣称完整发布。

## 5. 产品评估指标与保护指标

本章指标用于版本评审、抽样审查或用户研究，不代表 2.0.0 会在每个任务中自动采集遥测。Docs Harness 运行时不新增 metrics 命令、usage 解析或任务指标文件。

### 5.1 北极星：首次可用结果率

```text
first_usable_result_rate
= 用户无需任务级返工即可接受或进入最终用户验收的任务数
÷ 已结束任务数
```

“可用”要求结果与用户目标一致，不以 Harness 状态、测试数量或代码已修改代替。

### 5.2 核心效率指标

#### 可用结果交付时间

```text
time_to_usable_result_ms
= 从用户提出任务到首次交付可用结果或可验收运行环境的时间
```

包含 Harness、知识加载、规划、代码执行、构建、测试和等待用户处理不必要提示的全部时间。

#### 用户打断次数

```text
user_interruption_count
= 一个任务中要求用户确认、补充、授权或验收的次数
```

真正必要的 Codex 原生高风险授权和主观验收允许存在；Harness 补证、重复准入和无意义确认必须单独标记。

### 5.3 零容忍保护指标

#### 错误完成率

```text
false_complete_rate
= 宣称完成但关键行为没有直接证据、实际失败或关键验收层未完成的任务数
÷ 宣称完成的任务数
```

目标：`0`。

#### 未授权高风险动作

```text
unauthorized_high_risk_action_count
= 未经所需用户授权而执行删除、发布、推送、合并、外部写入等动作的次数
```

目标：`0`。

#### 未验证事项隐瞒

```text
undisclosed_unverified_item_count
= 已知未验证但最终答复未明确披露的关键事项数
```

目标：`0`。

### 5.4 暂不设置固定阈值的离线观察项

以下指标必须先记录真实基线，再决定正式门槛：

- 知识上下文 Token；
- 有效上下文密度；
- 方案生成耗时占比；
- 错误升级率；
- 用户验收步骤数；
- 首次验收通过率；
- 真实流程验收耗时。

除零容忍项外，2.0.0 不在缺少基线时虚设百分比和时长目标，也不为了测量这些指标增加任务运行时调用。

## 6. 两种工作模式

### 6.1 直接模式：默认

适用任务：

- 普通问答；
- 只读检查；
- Git 状态和历史查询；
- 已知文件或符号的小范围修改；
- 明确 Bug 修复；
- 单文件文档修改；
- Codex 已拥有足够上下文的任务。

流程：

```text
理解任务 → 读取必要文件 → 修改或回答 → 最小真实验收 → 回复用户
```

默认行为：

- 不创建 Harness 任务；
- 不调用 Run；
- 不生成 Gate；
- 不加载知识库；
- 不生成通用 Plan；
- 不调用旧 Verify；
- 不生成重准入循环。

核心指标：

- `direct_mode_false_escalation_rate`：本可直接完成却启用辅助或治理的比例；
- `time_to_first_productive_action_ms`：从任务开始到首次有效读取、修改或执行的时间；
- `unnecessary_harness_call_count`：直接任务中的 Harness 调用次数，目标为 0；
- `scope_drift_path_count`：范围外修改路径数量，目标为 0。

### 6.2 辅助模式：按需知识和方案

适用任务：

- 不知道代码位置；
- 需要理解项目架构；
- 涉及多个模块；
- 需要历史产品或技术约束；
- 用户明确要求方案；
- 修改影响面不清楚。

辅助模式不是一条新的强制流水线。知识和方案可以分别使用：

```text
直接执行 + 知识
直接执行 + 方案
直接执行 + 知识 + 方案
```

核心指标：

- `knowledge_activation_precision`：启用知识后确实使用了关键知识的任务比例；
- `must_have_knowledge_recall`：必要知识是否被找到；
- `effective_context_density`：模型可见知识中与当前任务直接相关的内容比例；
- `plan_activation_precision`：启用方案的任务中确实需要方案的比例；
- `plan_execution_alignment`：实际执行步骤与冻结方案关键步骤的一致程度；
- `assist_added_latency_ms`：辅助能力增加的时间。

### 6.3 Codex 原生安全边界：不是 Harness 模式

删除、Git 写入、发布、部署、安装、外部系统写入和其他不可逆动作，直接使用 Codex 自身的授权、沙箱和工具安全规则。Docs Harness 不接收这些动作、不生成风险标签、不签发授权文件，也不成为工具执行前置依赖。

产品要求只有两点：未授权高风险动作数为 0；Harness 为安全任务增加的调用数为 0。这两点分别由 Codex 原生安全层和 Harness 的“零介入”设计保证。

## 7. 端到端任务流程

### 7.1 环节一：任务理解

核心目标：准确理解用户要解决的问题、期望交付物和允许动作。

输入：

- 用户原始请求；
- 当前可见项目状态；
- 用户明确限制。

输出：

- 一句可执行目标；
- 必要的读写范围；
- 是否缺少阻断性信息；
- 当前是否准备执行高风险动作。

默认规则：

- 不为生成 Intent 标签而重新解释用户需求；
- 不要求模型输出完整分类合同；
- 可以通过安全、可逆的只读检查消除不确定性；
- 只有缺失信息会实质改变目标、范围或权限时才询问用户。

指标：

- `wrong_direction_rework_rate`；
- `first_understanding_acceptance_rate`；
- `unnecessary_clarification_count`；
- `objective_change_count`。

### 7.2 环节二：按需知识

核心目标：在 Codex 缺少关键项目事实时，以最少内容补足执行能力。

触发条件：

- 无法定位相关代码或模块；
- 需要架构、生命周期、数据流或历史约束；
- 代码和当前文档存在冲突；
- 用户问题本身是架构或项目知识问题。

禁止触发：

- 普通问答；
- 已知文件的简单修改；
- Git 操作；
- 只需直接搜索符号即可回答；
- 为了“完整理解项目”而宽泛加载。

知识加载顺序：

1. 直接文件、符号和当前源码；
2. 项目知识摘要；
3. 相关模块关系；
4. 必要历史决策；
5. 用户明确要求时再展开全文。

停止条件：

- 已定位目标文件或符号；
- 已理解直接影响方案的约束；
- 下一步已经是执行；
- 新内容不再改变目标、范围或验收。

输出合同：

```json
{
  "facts": ["与当前任务直接相关的事实"],
  "refs": ["文件、符号或知识引用"],
  "constraints": ["必须遵守的项目约束"],
  "omitted": ["被省略内容及原因"]
}
```

不输出：

- 候选卡片全集；
- 排序中间状态；
- 空数组和控制器快照；
- 无关知识正文；
- 自动维护建议。

指标：

```text
effective_context_density
= 直接影响目标、方案、执行或验收的知识 Token
÷ 模型可见知识总 Token
```

同时记录：

- `knowledge_added_tokens`；
- `irrelevant_knowledge_tokens`；
- `must_have_knowledge_miss_count`；
- `knowledge_reopen_count`；
- `knowledge_conflict_count`。

### 7.3 环节三：按需方案

核心目标：让复杂任务在执行前明确“做什么、不做什么、如何证明完成”。

触发条件：

- 用户明确要求先出方案；
- 跨模块、跨层或多阶段修改；
- 修改范围存在明显不确定性；
- 架构、迁移、发布、删除或高风险任务；
- 验收路径必须提前设计。

不触发：

- 普通问答；
- 只读检查；
- 单文件明确修改；
- 已有清晰复现和修复点的小 Bug；
- 简单 Git 查询或受控单动作。

方案生成前先选择两个维度：

```text
plan_level   = none | brief | full
plan_profile = general | frontend_ui | backend_service | bugfix | architecture | migration_release
```

`plan_level` 决定方案深度，`plan_profile` 决定领域字段。二者分开，避免把“任务复杂”误解为“所有领域字段都要填写”。

#### 方案深度选择

| 层级 | 适用情况 | 输出 |
|---|---|---|
| `none` | 普通问答、只读检查、明确单点修改 | 不生成方案 |
| `brief` | 用户要求简单方案、范围明确但需要列步骤 | 目标、范围、关键步骤、验收 |
| `full` | 跨模块、多阶段、架构、复杂产品或高风险任务 | 全面通用模板 + 必要领域字段 |

简单方案 Schema：

```json
{
  "objective": "用户目标",
  "scope": ["允许修改的范围"],
  "non_goals": ["明确不做的内容，仅有必要时出现"],
  "steps": ["关键执行步骤"],
  "risks": ["会改变执行或授权的真实风险"],
  "acceptance": ["能够直接覆盖用户目标的验收方式"]
}
```

全面通用模板保留当前模板的核心结构，并纠正执行前后的字段语义：

```text
背景
目标
非目标
成功标准
执行范围
执行内容
验收方案
风险与回滚（存在真实风险时）
```

1.x 的全面模板核心字段是“背景、目标、非目标、成功标准、执行内容、验收结果”。2.0.0 不删除这套全面结构，而是仅在 `full` 任务使用；执行前字段统一称为“验收方案”，实际执行完成后再产生独立的“验收结果”。

#### 领域模板选择

| Profile | 适用任务 | 在全面通用模板上增加的关键字段 |
|---|---|---|
| `general` | 不属于明确专用领域的复杂任务 | 不追加领域字段 |
| `frontend_ui` | 前端、桌面界面、产品交互和视觉状态 | 用户与场景、入口与流程、完整状态、组件与交互、视觉与响应式、可访问性、设计系统复用、真实页面验收 |
| `backend_service` | API、服务端、任务系统和数据处理 | 接口合同、数据模型、事务与一致性、并发与幂等、错误与重试、安全与隐私、性能容量、可观测性、兼容迁移 |
| `bugfix` | 已有功能行为偏离、回归和故障修复 | 精确复现、首次偏离、根因证据、修复边界、负向路径、回归范围 |
| `architecture` | 架构调整、公共合同和跨模块重构 | 当前约束、候选方案、取舍依据、最终决策、兼容策略、迁移与回滚 |
| `migration_release` | 数据迁移、版本升级、打包发布和外部交付 | 来源与目标、产物、兼容窗口、灰度步骤、数据保护、监控、回滚和交付分层 |

前后端同时变化时不创建第二份方案，也不机械拼接两套完整模板。使用一个 `full` 方案，以主 Profile 为骨架，只追加另一 Profile 中确实会改变执行或验收的字段。

规则：

- 没有内容的可选字段不发送；
- 不重复用户原文；
- 不包含 Gate 推导、候选讨论和控制器内部状态；
- 不要求模型填写 Harness 能确定生成的字段；
- 用户明确指定模板或要求使用全面模板时，用户选择优先；
- 不从任务正文关键词机械匹配模板，选择依据是实际修改面、交付物和验收方式；
- 模板选择结果只保留 `plan_level`、`plan_profile` 和简短原因，不把选择过程写进最终方案；
- 同一个方案允许组合少量领域模块，但不允许重复通用字段；
- 领域字段与任务无关时直接省略，不使用“无”“不适用”占位；
- 方案冻结后，执行阶段只消费目标、当前步骤、范围和验收；
- 实质范围变化时只更新差量，不重新生成整套合同。

指标：

- `plan_false_activation_rate`；
- `plan_missing_activation_rate`；
- `plan_scope_omission_count`；
- `plan_level_selection_accuracy`；
- `plan_profile_selection_accuracy`；
- `irrelevant_plan_field_rate`；
- `missing_domain_field_count`；
- `plan_rework_count`；
- `plan_execution_alignment`；
- `plan_acceptance_traceability`：每项成功标准是否能追溯到验收步骤；
- `plan_generation_latency_ms`；
- `plan_token_share`：方案 Token 占完整任务累计输入的比例，仅作为观察指标。

### 7.4 环节四：代码和任务执行

核心目标：以最短、安全路径完成用户目标，避免被辅助系统打断。

执行规则：

- 只读取当前步骤真正需要的文件；
- 优先直接搜索文件、符号和调用链；
- 保留用户已有和其他任务改动；
- 修改范围以用户目标和当前步骤为准；
- 构建、测试和运行只选择能够覆盖本次变化的最小集合；
- 高风险动作按 Codex 原生授权与沙箱规则执行，Harness 不增加调用；
- 不为了更新 Harness 状态重复读取、重复测试或补证。

指标：

- `execution_lead_time_ms`；
- `scope_drift_path_count`；
- `duplicate_read_count`；
- `duplicate_verification_count`；
- `tool_failure_count`；
- `user_change_preservation_violation_count`，目标 0。

### 7.5 环节五：原生风险与授权边界

核心目标：不重复建设 Codex 已有的安全能力，也不让 Harness 成为所有工具动作的串行前置依赖。

执行规则：

- 删除、Git 写入、发布、安装和外部系统写入直接走 Codex 原生授权与沙箱；
- Harness 不接收 action、effects、authorization 或 scope；
- Harness 不返回 allow/block，不生成授权文件，不验证用户授权真伪；
- Codex 原生安全层要求用户确认时，按原生交互完成，不把确认结果回灌 Harness；
- 安全、只读和普通修改不会因为 Harness 增加任何风险检查调用。

验收标准：`harness_risk_control_call_count=0`；源码、CLI、测试和包中不存在新流程的 Gate、preflight、Host Adapter 或 usage metrics 实现。

### 7.6 环节六：真实功能验收

核心目标：直接验证用户要求的行为是否真的工作。

验收不再以旧 Verify 为中心，而以修改面和用户目标为中心。

#### 最小充分验收原则

选择成本最低、但能够直接覆盖本次行为的验收层。成本更低但不能覆盖行为的检查，不得代替真实验收。

| 修改面 | 最小充分验收 |
|---|---|
| 纯函数、算法、格式化 | 聚焦单元测试或直接输入输出检查 |
| 模块、API、数据流 | 启动最小服务并调用真实接口 |
| Web UI | 启动页面并走真实交互路径 |
| 桌面应用 | 启动本地应用并复现目标流程 |
| macOS 权限、窗口、语音、托盘 | 本地真机运行态回归 |
| 构建、打包 | 实际构建并检查产物内容和可启动性 |
| 安装、升级 | 安装真实产物后重新启动验证 |
| 外部集成 | 在授权环境中执行真实或受控沙箱调用 |
| 主观体验、视觉和硬件 | 准备运行环境并交给用户验收 |

#### 验收层级

```text
L1 源码一致性：lint、类型、编译、静态合同
L2 聚焦行为：单元、接口、组件或命令测试
L3 本地运行态：真实应用或服务流程
L4 构建/包/安装：真实产物层
L5 用户可见验收：主观体验、权限、硬件和最终业务结果
```

规则：

- 每项完成声明必须标注已接受的最高层；
- L1 不能冒充 L3；
- 本地源码通过不能冒充 DMG 已验证；
- DMG 生成不能冒充已安装；
- Codex 无法执行 L5 时必须明确交给用户；
- 同一行为、依赖、环境和夹具未变化时可以复用有效证据，不重复跑全量测试；
- 失败只报告真实失败原因和下一步，不返回控制状态全集。

指标：

- `behavior_claim_direct_evidence_rate`；
- `runtime_flow_execution_rate`；
- `acceptance_layer_accuracy`；
- `false_complete_rate`，目标 0；
- `verification_latency_ms`；
- `verification_command_count`；
- `verification_reuse_count`；
- `contract_only_claimed_behavior_count`，目标 0。

### 7.7 环节七：用户验收交接

核心目标：Codex 无法独立判断时，把用户验收成本降到最低。

Codex 必须先完成自己能够完成的部分：

- 构建或启动运行环境；
- 准备测试数据；
- 打开目标页面或应用；
- 执行能够自动执行的前置流程；
- 把系统停在需要用户判断的位置。

交接格式：

```text
已自动验证：
- 代码编译通过
- 本地服务启动成功
- 目标接口返回预期数据

请用户验证：
- 点击麦克风后系统权限提示是否正确
- 退出托盘后旧内容是否再次注入

最短操作：
1. 点击开始录音
2. 说一句测试文本
3. 从托盘退出并观察目标输入框
```

指标：

- `user_handoff_completeness`，目标 100%；
- `user_acceptance_step_count`；
- `first_user_acceptance_pass_rate`；
- `undisclosed_unverified_item_count`，目标 0；
- `environment_ready_before_handoff_rate`。

### 7.8 环节八：可选验收记录

核心目标：用户或任务明确需要留档时，只保存真实验收事实；普通任务不自动记录。

允许记录：验收层级、状态、真实证据文件引用、失败原因和下一步。知识查询与方案文件各自保存自身必要信息，不合并为任务遥测。

禁止记录：

- 凭据和令牌；
- 私密聊天全文；
- 无关用户数据；
- 模型完整推理过程；
- 未经授权的长期记忆；
- 自动更新项目知识库；
- Token、时长、用户授权或完整工具历史。

验收记录不会自动进入后续模型上下文。需要复用时，由 Codex 按用户目标直接读取具体证据文件。

## 9. Verify 语义重构

### 9.1 拆分三个概念

#### Contract Check

检查范围、格式、授权和记录一致性。它属于内部控制，不代表功能正确。

#### Behavior Acceptance

运行测试、真实接口、应用流程、构建、安装或受控人工验收，直接验证用户目标。

#### User Acceptance

由用户判断主观体验、权限、硬件或 Codex 无法操作的真实环境。

独立 CLI 不能证明确认动作来自用户，因此当前只允许登记 `user_pending`，拒绝 `user_acceptance + passed` 的自我声明；最终通过由用户直接确认，不由 Harness 代填。

三者必须分开报告，不得用 Contract Check 通过代替 Behavior Acceptance。

### 9.2 2.0.0 命名建议

- 新接口使用 `acceptance` 或 `accept`；
- `verify` 不属于 2.0.0 CLI，2.0.0 不读取旧状态；
- 2.0.0 的 `acceptance record` 必须区分 `contract_checked` 与 `behavior_verified`；
- 没有行为证据时不能进入完整完成状态。

### 9.3 最小失败响应

```json
{
  "status": "failed",
  "layer": "local_runtime",
  "reason": "退出托盘后旧文本再次注入",
  "next_action": "修复退出阶段重复 finalize 后重跑同一流程"
}
```

不返回完整 changed paths、Gate、收据、证据骨架和合同快照。

## 10. 知识库产品合同

### 10.1 定位

知识库是按需项目事实提供器，不是会话启动包。

### 10.2 真源优先级

根据问题类型选择真源：

- 当前行为：当前源码、运行态和真实产物；
- 架构合同：ADR、架构文档和明确接口；
- 模块定位：符号、调用链和目录结构；
- 历史原因：版本记录、任务证据和知识摘要；
- 用户体验：真实运行和用户反馈。

知识库与当前源码冲突时必须显式显示冲突，不允许静默覆盖。

### 10.3 输出要求

- 摘要优先；
- 引用可追溯；
- 与任务目标直接关联；
- 可增量展开；
- 不自动维护；
- 不因全局 scope 自动命中；
- 不把候选排序过程发给模型。

### 10.4 质量指标

- `must_have_knowledge_recall`；
- `knowledge_activation_precision`；
- `effective_context_density`；
- `knowledge_conflict_visibility_rate`；
- `stale_knowledge_usage_count`；
- `knowledge_load_latency_ms`。

## 11. 方案模板产品合同

### 11.1 定位

方案模板是复杂任务的执行压缩器，不是项目管理表格。

当前全面模板不会被删除。2.0.0 将其升级为 `full/general` 通用模板，并通过 `plan_level` 和 `plan_profile` 选择适当深度和领域字段。

### 11.2 模板选择优先级

按以下顺序决定模板：

1. 用户明确指定的模板、格式或“使用全面模板”要求；
2. 用户明确要求简单方案、详细方案或先做产品设计；
3. 实际交付物和修改面；
4. 任务复杂度、阶段数、跨模块范围和验收难度；
5. 无法可靠判断时使用 `brief/general`，在发现复杂度实质增加后再升级，不预先加载所有字段。

模板选择不得依赖单个关键词。例如任务包含“页面”不一定是 `frontend_ui`；只有真实交付涉及界面、状态、交互或视觉验收时才启用前端字段。

选择结果使用紧凑合同：

```json
{
  "plan_level": "full",
  "primary_profile": "frontend_ui",
  "secondary_profiles": ["bugfix"],
  "template_versions": ["full/v1", "frontend-ui/v1", "bugfix/v1"],
  "reason": "涉及桌面交互完整状态，并需要复现和修复现有行为偏离"
}
```

`reason` 只说明决定模板的实际修改面，不展开推理过程。`secondary_profiles` 默认为空，只有缺少其中字段会导致执行或验收遗漏时才添加。

### 11.3 方案层级

#### `none`

不创建方案文件。Codex 直接执行并验收。

#### `brief`

只包含：

- 目标；
- 执行范围；
- 关键步骤；
- 验收方案。

适合明确、小范围、但用户希望先看到做法的任务。

#### `full`

保留并扩展当前全面模板：

- 背景；
- 目标；
- 非目标；
- 成功标准；
- 执行范围；
- 执行内容；
- 验收方案；
- 风险与回滚，仅在存在真实风险时出现。

`full` 仍然遵守“无关字段不出现”。全面指覆盖复杂任务的关键决策面，不等于把所有领域模板拼成一张表。

### 11.4 通用字段语义

| 字段 | 核心问题 | 禁止内容 |
|---|---|---|
| 背景 | 为什么现在需要做、当前状态是什么 | 复制完整用户对话和无关项目历史 |
| 目标 | 用户最终获得什么 | 把技术动作当成用户结果 |
| 非目标 | 明确排除哪些容易越界的内容 | 为了完整而罗列显然无关事项 |
| 成功标准 | 什么可观察结果代表成功 | “代码写完”“测试很多” |
| 执行范围 | 允许修改哪些模块、文件或系统 | 模糊的全仓库范围 |
| 执行内容 | 按依赖顺序说明关键实现 | 逐行代码预写和无决策价值的步骤 |
| 验收方案 | 用什么真实流程覆盖成功标准 | 预填尚未产生的“验收通过” |
| 风险与回滚 | 哪些失败会产生真实影响、如何恢复 | 通用风险套话 |

### 11.5 领域 Profile

#### 前端与产品界面：`frontend_ui`

用于 Web、桌面界面、产品交互、视觉流程和状态呈现。按任务需要选择：

- 用户、场景和核心任务；
- 入口、导航和主流程；
- 完整状态矩阵：初始、加载、空、成功、失败、禁用、中断和恢复；
- 信息架构、组件职责和状态归属；
- 交互反馈、文案和错误恢复；
- 视觉层级、布局、响应式和平台差异；
- 可访问性、键盘、焦点和读屏要求；
- 现有设计系统、组件和样式复用；
- 真实页面或桌面运行态验收。

前端方案的核心不是组件清单，而是用户流程和完整状态是否闭环。

#### 后端与服务：`backend_service`

用于 API、服务端、后台任务、数据处理和公共模块。按任务需要选择：

- 接口输入、输出、错误和兼容合同；
- 数据模型、存储和生命周期；
- 事务、一致性、并发和幂等；
- 超时、重试、降级和恢复；
- 安全、权限、隐私和敏感数据边界；
- 性能、容量和资源限制；
- 日志、指标、追踪和故障定位；
- 版本兼容、数据迁移和回滚；
- 接口、服务和真实数据流验收。

后端方案的核心不是罗列技术组件，而是接口、数据和失败语义是否明确。

#### Bug 修复：`bugfix`

用于功能偏离和回归：

- 用户原始复现；
- 发生前后的完整时间线；
- 首次偏离正确行为的位置；
- 根因证据；
- 修复边界和明确不改内容；
- 正向、负向和回归验收。

不得用通用“可能原因”代替首次偏离和根因证据。

#### 架构：`architecture`

用于公共合同和跨模块结构调整：

- 当前状态和硬约束；
- 候选方案及其真实取舍；
- 最终决策和原因；
- 模块边界和接口；
- 兼容策略；
- 迁移顺序；
- 回滚和替代路径。

#### 迁移与发布：`migration_release`

用于数据迁移、版本升级、包、安装和外部交付：

- 来源、目标和所有权；
- 版本、产物和环境；
- 兼容窗口和灰度顺序；
- 数据备份、恢复和幂等；
- 监控、停止条件和回滚；
- 源码、包、安装、下游和用户验收分层。

### 11.6 组合规则

- 一个任务只有一份主方案；
- 一个方案只有一组通用字段；
- 指定一个主 Profile；
- 最多追加真正必要的其他 Profile 字段，不复制完整次级模板；
- 全栈任务通常使用 `full`，以前端或后端中决定用户结果和验收的主要修改面为主 Profile；
- Bug 修复可以与前端或后端组合，但 `bugfix` 只追加复现、根因和回归字段；
- 架构、迁移和发布字段只在真实影响对应边界时出现；
- 用户指定全面模板时使用 `full`，但仍可以根据领域替换或补充专用字段。

### 11.7 必填、条件必填与省略

始终必填：

- `objective`；
- `scope`；
- `steps`；
- `acceptance`。

仅必要时出现：

- `non_goals`；
- `risks`；
- `dependencies`；
- `user_decisions`。

领域字段采用“影响执行或验收才必填”的原则。字段不相关时直接不存在，不填写“无”“不适用”或空数组。

### 11.8 模板注册与版本

模板不继续硬编码为 Gate 的附加字段。建议使用版本化注册表：

```text
plan-templates/
├─ levels/brief.json
├─ levels/full.json
└─ profiles/
   ├─ general.json
   ├─ frontend-ui.json
   ├─ backend-service.json
   ├─ bugfix.json
   ├─ architecture.json
   └─ migration-release.json
```

每个模板声明：

- `template_id`；
- `schema_version`；
- 适用交付物和修改面；
- 必填字段；
- 条件字段；
- 验收要求；
- 与其他 Profile 的组合规则。

模板升级必须记录版本；已经冻结的方案继续绑定原模板版本，不因注册表更新自动增加字段。

### 11.9 禁止内容

- 通用背景套话；
- 空字段；
- Gate 和规则重复；
- 证据模板；
- Harness 内部状态；
- 多个候选方案的完整讨论；
- 与执行无关的历史知识。

### 11.10 方案成功指标

方案只有在以下情况才产生价值：

- 减少范围遗漏；
- 减少执行返工；
- 提前明确验收路径；
- 帮助用户确认重要产品决策。

字段完整率和文档长度不是成功指标。

同时记录：

- `plan_level_selection_accuracy`；
- `plan_profile_selection_accuracy`；
- `irrelevant_plan_field_rate`；
- `missing_domain_field_count`；
- `template_override_count`；
- `plan_rework_count`；
- `plan_execution_alignment`；
- `plan_acceptance_traceability`。

### 11.11 ADR 写作与复审

ADR 不是所有复杂方案的默认附属文档。只有决策会长期约束以下内容时才写：

- 架构边界或模块职责；
- 公共接口、数据合同或兼容策略；
- 安全、隐私、权限或数据一致性；
- 基础设施、部署、迁移或不可逆选择；
- 对既有 ADR 的替代。

普通 Bug、局部重构、临时实验、实现笔记和纯视觉样式不写 ADR。

写作流程：

```text
确认需要架构决策
→ 主 Codex 读取当前源码、架构文档和相关 ADR
→ 比较候选与真实取舍
→ 冻结最终决策
→ 主 Codex 写 ADR
→ 必要时只读复审
→ 主 Codex 修订并进入实现
```

ADR 使用 `plan_level=full + plan_profile=architecture`，其中 `adr_decision` 必须明确：不需要 ADR、创建新 ADR 或 supersede 既有 ADR。内容至少包括：状态、日期、范围、上下文、决策、候选、取舍、影响、兼容与迁移、回滚或替代、验收、引用以及 supersession 关系。

主 Codex 是唯一写作者。只有复杂、高风险、跨模块、安全、迁移或不可逆决策才建议调用只读子智能体复审；复审只检查替代方案覆盖、事实一致性、边界、兼容、迁移、回滚和验收，不直接修改 ADR。用户仍负责产品方向、长期成本和不可逆边界的最终选择。

已接受 ADR 不原地改写决策内容。后续改变决策时创建新 ADR，并通过 `Supersedes` / `Superseded by` 保留历史；仅拼写、链接和不改变语义的修正可以原地修改。

ADR 成功指标是必要性准确率、实现可追溯、候选覆盖、迁移完整和 supersession 正确，不以 ADR 数量或篇幅为指标。

## 12. 风险与授权边界

Docs Harness 2.0.0 不提供 Gate、动作 preflight、授权文件或 Host Adapter。删除、Git 写入、发布、部署、安装、外部系统写入和其他不可逆动作的识别、授权与阻断完全由 Codex 原生工具权限和沙箱承担。

Harness 在这一环节的产品合同是“零介入”：不接收动作，不判断授权，不生成收据，不要求模型解释风险，也不保存用户授权。这样既避免第二套控制系统产生误判，也避免所有任务被迫多走一次串行调用。

## 13. 模型上下文合同

### 13.1 直接模式

Harness 增加的模型可见 Token 必须为 0。

### 13.2 知识辅助

模型只接收：

- 与当前目标直接相关的事实；
- 引用；
- 必须遵守的约束；
- 省略提示。

### 13.3 方案辅助

执行模型只接收：

- 最终方案；
- 当前步骤；
- 允许范围；
- 验收方式。

### 13.4 原生安全

Codex 原生安全提示直接由宿主呈现；Harness 不向模型注入任何风险控制内容。

### 13.5 验收

模型只接收：

- 通过及接受层；或
- 唯一失败原因和下一步。

### 13.6 控制面隔离

以下内容不得默认进入模型上下文：

- 完整任务包；
- Gate 派生图；
- 规则全文；
- 空 Plan Skeleton；
- 完整 Evidence 清单；
- Receipt 历史；
- 工作区无关漂移；
- Verify 内部合同快照；
- Readmission 全量状态。

## 14. 产品架构

### 14.1 组件

```text
Codex Direct Executor
├─ Optional Knowledge Provider
├─ Optional Plan Selector + Template Registry
└─ Optional Acceptance Recorder
```

### 14.2 职责

| 组件 | 负责 | 不负责 |
|---|---|---|
| Codex Direct Executor | 理解、执行、调用工具、回复用户 | 维护 Harness 控制闭环 |
| Knowledge Provider | 按需提供相关项目事实 | 会话启动自动注入、自动维护知识 |
| Plan Selector + Template Registry | 按复杂度选择 none/brief/full，并按领域组合模板字段 | 用一套模板强迫所有任务填表 |
| Acceptance Recorder | 按明确请求保存验收层、状态和真实证据引用 | 自动运行测试、自动采集指标、用合同检查代替功能正确性 |

### 14.3 Codex 原生能力边界

独立会话、原生授权、沙箱、工具权限和 usage 事件都属于 Codex 产品能力，不是 Docs Harness 2.0.0 的组件。Harness 不封装、不代理，也不对其结果建立二次声明。

## 15. 数据与评估

### 15.1 不建立运行时任务遥测

2.0.0 不新增 metrics 命令、任务指标 JSON、Codex usage 解析或自动事件采集。知识查询、方案文件和可选验收记录只保存各自完成产品功能所需的最小数据。

需要评估版本效果时，通过明确的只读审查从现有会话日志、任务结果和用户反馈中抽样计算，不让每个业务任务为未来统计预付成本。

### 15.2 数据原则

- 默认不保存任务指标；
- 不保存原始用户聊天；
- 不保存凭据和私密数据；
- 不保存完整模型推理；
- 用户验收和自动验收分开；
- 评估数据不进入模型业务上下文；
- 无法从真实来源得到的数据不推断、不补零。

### 15.3 反指标

以下数字不再作为产品成功指标：

- Gate 数量；
- Verify 次数；
- Plan 字段数量；
- Evidence 文件数量；
- Receipt 数量；
- 测试总数量；
- Harness 响应完整度；
- 单纯 Token 降幅。

## 16. CLI 与宿主接口建议

2.0.0 不要求普通任务调用任何 Harness 命令。

按需能力建议拆分为：

```text
knowledge query     按需查询项目知识
plan select         返回 plan_level、plan_profile 和模板版本
plan create         按已选层级和领域生成方案
acceptance record   记录真实验收层和结果
```

旧接口：

```text
run
context
progress
verify
```

迁移原则：

- 从 CLI 与控制器删除旧命令；
- 删除 `--legacy-opt-in`，不保留旧流程兼容入口；
- 迁移指南直接列出替代接口；
- 不读取、创建或继续旧任务；
- `task`、`background`、`authorization` 和知识维护 Job 从当前 CLI 删除。

## 17. 实施阶段

### P0：默认直跑与旧流程移除

目标：先停止负收益默认行为。

实施：

- 从 SKILL.md、README 和宿主入口移除普通任务必须 Run 的要求；
- 普通问答、只读检查、明确小修改默认不创建 Harness 状态；
- 关闭知识自动加载、通用 Plan、任务级 Gate 和默认 Verify；
- 删除旧四个入口和 opt-in 解析代码；
- 删除旧规则、后台治理、任务控制和知识维护的产品入口；
- 保证关闭 Harness 时 Codex 可以完整工作。

验收：

- 直接任务 Harness 调用数为 0；
- 现有项目不安装 Harness 也能执行普通任务；
- 高风险工具继续由 Codex 原生权限和沙箱保护；
- 旧任务状态不会阻断新任务。

### P1：真实验收流程

目标：先把“完成”定义改正确。

实施：

- 新增 acceptance layer 和状态；
- Contract Check、Behavior Acceptance、User Acceptance 分离；
- 根据修改面选择最小充分验收；
- Codex 可执行的真实流程由 Codex运行；
- 无法自动验收时生成最短用户验收交接；
- 最终回复强制区分已验证、待用户验证和未验证。

验收：

- false complete 为 0；
- L1 不得声明 L3；
- 用户验收交接完整率 100%；
- 旧 Verify 不再把合同检查称为功能验证。

### P2：按需知识

目标：恢复最初的项目知识价值，不恢复自动注入。

实施：

- 提供显式 `knowledge query`；
- 直接源码和符号优先；
- 摘要和引用优先；
- 相关性、冲突和省略可见；
- 不自动维护知识；
- 不将候选和排序过程送入模型。

验收：

- 直接模式知识注入为 0；
- 必要知识可按需找到；
- 无关知识不会因 scope 自动命中；
- 冲突不会静默隐藏。

### P3：按需方案

目标：保留全面模板的价值，同时让简单、前端、后端、Bug、架构和迁移任务获得匹配自身决策面的方案。

实施：

- 增加 `plan_level=none|brief|full`；
- 增加 `plan_profile=general|frontend_ui|backend_service|bugfix|architecture|migration_release`；
- 保留当前全面模板为 `full/general`，将执行前“验收结果”调整为“验收方案”；
- 提供 brief 模板和版本化领域模板注册表；
- 支持一个主 Profile 和少量必要的跨领域字段组合；
- 用户明确指定全面模板、简单模板或领域模板时优先采用用户选择；
- 删除空骨架和重复控制字段；
- 领域无关字段直接省略，不填写“不适用”；
- 执行阶段只接收冻结方案投影；

## 20. 迁移策略

### 20.1 pre-2.0 项目

- 所有旧项目统一升级到 `project-config/v6`，不保留兼容模式；
- preview 只读列出 `remove / preserve / conflict`，apply 才写入；
- 指纹归属明确的旧规则、已识别知识地图、受管版本区块和旧 Runtime 删除；
- 项目知识正文、ADR、TODO、方案、质量账本、Repowiki 和归属不明文件保留；
- 旧 Run/Verify 即使带 opt-in 也不能继续状态；
- 重复 upgrade 必须幂等，符号链接和所有权冲突必须零写入失败关闭。

### 20.2 ZBuddy

建议迁移顺序：

1. 先在 ZBuddy 项目说明中确认默认不调用 Harness；
2. 引入按需知识规则；
3. 引入最小方案模板；
4. 引入真实验收交接格式；
5. 确认高风险动作继续使用 Codex 原生安全能力；
6. 不接入 Harness Gate、preflight、Host Adapter 或 metrics。

### 20.3 回滚

- 2.0.0 各可选能力独立开关；
- 知识、方案或验收记录出现问题时可以单独关闭；
- 关闭所有可选能力后仍可回到 Codex 直接执行；
- 2.0.0 不提供恢复 1.x 强制闭环的运行开关；
- 应用失败时按 preview、工作区差异和版本控制恢复本次受管文件；降级旧软件包属于独立版本恢复，不是 2.0.0 模式。

| 高风险动作安全 | 完全使用 Codex 原生授权与沙箱，不由 Harness 重复判断 |
| 取消旧 Verify 后验收不足 | acceptance layer、最小充分验收和 false complete 零容忍 |
| Codex 无法操作真实环境 | 启动最小环境并交给用户，完整披露未验证项 |
| 知识短但不准确 | 必要召回、冲突可见、当前源码优先 |
| 方案再次变成填表 | plan_level 分级、无关字段省略、简单任务不生成 |
| 前后端等不同任务被套用同一模板 | 领域 Profile 注册表、实际修改面选择、用户指定优先 |
| 全栈任务拼接多套模板导致方案膨胀 | 单一主方案、一个主 Profile、次级 Profile 只追加必要字段 |
| 模板自动选择错误 | 选择结果可见、用户可覆盖、记录选择准确率和方案返工 |
| 指标系统重新污染上下文 | 不提供运行时 metrics 命令，不解析 usage，只做明确发起的离线审查 |
| 旧宿主依赖 Run/Verify | 重大版本、单向迁移预览、CLI 明确删除和迁移说明 |
| 历史 Host Adapter 形成沉没成本 | 从源码、测试、包和当前方案中删除，不保留未来接入占位 |
| 版本号被误报为已发布 | 版本真源、包、fresh clone、下游和用户验收分层报告 |

## 22. 冻结设计决策

以下决策在 2.0.0 方案中冻结：

1. 普通任务默认不使用 Harness；
2. 用户显式声明不用 Harness 时必须尊重，除宿主原生安全控制外不得暗中恢复旧流程；
3. 知识和方案是独立、按需能力；
4. 新任务不提供 Gate、Harness preflight 或第二套授权；
5. 高风险动作完全使用 Codex 原生授权与沙箱；
6. Verify 不再代表 Harness 合同核验；
7. 功能正确性必须由直接行为证据支持；
8. Codex 能自动完成的真实流程必须由 Codex执行；
9. Codex 不能完成的验收必须准备最低成本环境并交给用户；
10. 所有未验证事项必须披露；
11. Harness 不建立任务级控制状态或运行时 usage 遥测；
12. Host Adapter、preflight 和 metrics 从源码、测试、包和当前方案中移除；
13. 不要求额外 A/B 才允许默认关闭 Harness；
14. 除零容忍项外，不在缺少基线时虚设量化门槛；
15. 2.0.0 只有在全部发布层证据完成后才能宣称已发布。
16. 方案采用复杂度层级和领域 Profile 双维选择；当前全面模板保留为复杂任务基础，简单任务不被强制套用。
17. ADR 由主 Codex 编写；只有复杂、高风险或不可逆架构决策才可选只读子智能体复审，子智能体不作为默认写作者。

## 23. 2.0.0 完成定义

只有同时满足以下条件，才能宣称 Docs Harness 2.0.0 完成：

1. 普通任务默认不调用 Harness；
2. 用户显式关闭 Harness 时不存在隐式 Run、Gate、Plan、Verify 或 Readmission；
3. 按需知识不会自动注入，且必要事实可追溯；
4. 简单任务不生成方案，复杂任务方案能够直接执行；
5. 新流程不存在任务级 Gate、Harness preflight、Host Adapter 或 metrics；
6. 高风险动作继续由 Codex 原生授权和沙箱保护；
7. Harness 风险控制调用数为 0；
8. Contract Check、Behavior Acceptance 和 User Acceptance 分开；
9. 错误完成率为 0；
10. 未验证事项隐瞒数为 0；
11. Codex 可执行的真实流程已经实际执行；
12. Codex 不可执行的验收已经准备环境和最短用户步骤；
13. 直接模式没有 Harness 控制状态和运行时遥测；
14. 旧 Run/Verify 与 `--legacy-opt-in` 不存在于 CLI 或控制器；
15. 受影响面聚焦测试通过；行为、依赖和夹具未变化的历史绿色证据允许复用，不机械要求每次全量回归；
16. `VERSION`、`package.json`、SKILL frontmatter 和源码版本常量一致为 2.0.0；
17. npm 包包含所有正式实现文件；
18. fresh clone 可安装和运行；
19. ZBuddy managed upgrade preview 只有预期变化；
20. 源码、包、提交、推送、下游、安装和用户验收分别提供证据；
21. 没有用方案文档、版本号、测试数量或本地源码代替发布完成。
22. brief、full 和各领域 Profile 均有版本化模板与选择回归；
23. 前端、后端、Bug、架构和迁移方案包含各自必要字段，不包含无关领域填表；
24. 用户明确指定模板时，实际方案采用用户选择并保持可追溯。
25. 架构方案明确 `adr_decision`，已接受 ADR 通过新 ADR supersede，不原地重写历史决策。
26. 当前合同、架构、测试、TODO 和方案目录只描述 2.0.0；历史方案与审查归档且不进入默认知识查询或 npm 对外文档集合。
27. 项目升级只剥离 Harness 受管版本区块，不重写项目正文或给旧正文贴 2.0.0 标签。
28. fresh init 不安装旧规则，不创建旧知识、后台或任务 Runtime。
29. pre-2.0 upgrade preview 零写入并逐路径给出删除、保留和冲突清单。
30. apply 删除所有权明确的旧规则、知识地图、受管版本区块和旧 Runtime，同时保留项目文档、质量账本与归属不明内容。
31. `project-config/v6` 不含规则、Gate、旧 Verify、后台治理或 opt-in 字段。
32. 重复 upgrade 幂等；不安全符号链接和覆盖冲突在任何安装写入前失败关闭。
